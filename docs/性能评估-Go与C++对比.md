# Go 还是 Go+C++？—— 基于实测的性能评估

> 结论日期：2026-10-01
> 评估对象：OKX 全合约量化终端（`C:\Users\Administrator\Documents\finally`）
> 触发问题：「项目所有文件能不能全部热插拔？全部用 C++ 编成 DLL 让 Go 调用会不会更快？」

---

## 〇、结论先行

| 问题 | 结论 |
|---|---|
| 全部用 C++ 编 DLL 给 Go 调，会更快吗？ | **不会。** 实测本系统 **99.8% 的墙钟时间花在等网络/等数据库**，纯计算只占 0.2%。把计算加速到「零耗时」，整机也只快 0.2%。 |
| Go + C++ 更快更好吗？ | **对这份代码是更慢更差。** cgo 要装 MinGW 工具链、破坏交叉编译、双语言维护；换来的收益是负的（见 §三）。 |
| 那瓶颈在哪？ | **两个具体的实现缺陷**，都在 Go 里，都是几百行能修的（见 §五）。 |
| 全部文件热插拔能做吗？ | **配置层已经做完了**；代码层热插拔在 Windows 上不成立（见 §四）。 |

**一句话**：这个系统的瓶颈是「把 136 万行已在本地 MySQL 里的 K 线，每轮又从 OKX 重新下载一遍」——这是**架构选择问题**，不是**编程语言问题**。C++ 救不了架构。

## 一、实测证据（全部可复现）

### 1.1 工具链现实：这台机器上根本没有 C++ 编译器

```
gcc       (缺)      g++       (缺)      cl        (缺)
clang     (缺)      cgo       (缺)      x86_64-w64-mingw32-gcc (缺)
MSVC / Visual Studio：(无)
Go 环境：CGO_ENABLED=0   CC=gcc
```

`CGO_ENABLED=0` 是 Go 在**找不到 C 编译器时的自动降级**。要走 C++ 路线，第一步就得先装完整的 MinGW-w64 或 MSVC 工具链——这件事本身对 2 核/4G 的目标机是个不小的负担。

## 二、核心论证：Amdahl 定律下的天花板

`signal.recalc` 一轮要对 **176 个可交易合约**各算一次信号。代入实测值：

```
纯计算耗时 = 176 × 335.9 µs            = 59.1 ms
墙钟耗时   = 28,700 ms（实测平均）
────────────────────────────────────────────────
计算占比   = 59.1 / 28,700             = 0.21%
```

`feed.refreshLatest` 更极端：

```
纯计算耗时 = 479 × 335.9 µs            = 160.9 ms
墙钟耗时   = 44,600 ms（平均） / 753,300 ms（最大）
────────────────────────────────────────────────
计算占比   = 0.36%（平均） / 0.021%（最大）
```

**就算 C++ 把计算加速到无限快（耗时归零）：**

| 场景 | 现在 | C++ 无限加速后 | 提升 |
|---|---|---|---|
| `signal.recalc` | 28,700 ms | 28,641 ms | **0.21%** |
| `refreshLatest`（平均） | 44,600 ms | 44,439 ms | **0.36%** |
| `refreshLatest`（最大） | 753,300 ms | 753,139 ms | **0.021%** |

而 C++ 在真实世界里不可能无限快。对这堆指标运算，Go 编译后是原生机器码，与优化过的 C++ 差距通常在 **1.5~3 倍**，乐观取 3 倍：

```
实际收益 = 0.21% × (1 - 1/3) = 0.14%
```

**为 0.14% 的收益，重写 24,000 行代码 + 引入双语言工具链 + 承担 cgo 的全部风险。这个交易不成立。**

## 三、cgo 的隐性成本（为什么 Go+C++ 往往「更慢」而不是「更快」）

很多人以为「C++ 快 → 调 C++ 就快」，实际 cgo 有四项固定开销，**且第一项对本项目是致命的**：

### 3.1 跨语言数据传递要拷贝（本项目最致命）

`ComputeSignal` 的输入是 1500 根 Candle（每根 40+ 字节 = 60 KB+）。走 cgo 的话：

* 每次调用都要把整个切片 **memcpy 过边界**——430 ms 的墙钟里，拷贝本身就不便宜；
* 要靠 C++ 拿到净收益，**必须让 K 线常驻在 C++ 堆里**（C++ 自己持有缓冲区、自己增量更新）；
* 那就等于把「K 线存储 + 增量更新 + 生命周期管理」整个搬到 C++ ——
  这不是「让 Go 调个库」，这是**把项目的心脏换掉**。

### 3.2 每次调用有固定开销

Go → C 的函数跳转约 **50~200 ns**（含 goroutine 抢占、栈切换检查）。本项目每轮扫描 176~479 次调用 → 合计 **0.01~0.1 ms**。这项本身可忽略，但说明**逐根 K 线调用 C++ 是错误用法**；正确用法是**批量接口**（一次传 N 根，回 N 个 mask）。

### 3.3 cgo 调用会占住 OS 线程

Go runtime 在 cgo 调用期间无法把那颗 P 调度给别的 goroutine，且 cgo 调用**不参与 Go 的抢占式调度**。本项目只有 **2 核**，一次长 cgo 调用会让一半算力卡住。

### 3.4 工具链与部署成本

* 目标机上必须装 MinGW-w64 / MSVC（现在一个都没有）；
* 失去 `CGO_ENABLED=0` 带来的纯净静态编译与秒级交叉编译；
* 二进制体积增大，且要多带一份 `libstdc++-6.dll` / `libgcc_s_seh-1.dll`；
* 崩溃从「Go panic + 堆栈」退化为「整个进程段错误」，没有 recover 可言——**对一个管理真金白银的自动交易进程，这是实打实的风险升级**。

## 四、「全部文件热插拔」到底能做到什么

「热插拔」有三种截然不同的含义，可行性差距极大：

### 4.1 配置热插拔 ✅ **已经做完了**

`configs/okx_strategy.json` 已实现热插拔（见 `docs/架构说明.md` §二十）：

* `service.StrategyStore` 每轮 `stat` → mtime/size 变了才重读 → 再用内容 `sha256` 确认「真的变了」（防止编辑器另存触发全市场重算）；
* 改完保存，**看门狗 2 秒内重跑准入过滤**，symbolList / 下单金额 / 止盈参数全部即时生效；
* 读失败**沿用上一份好配置**，绝不打回默认值；
* 已实测：`max_order_margin_usdt` 1.5 → 0.4 → 1.5，symbolList `176 → 167 → 176`，**全程零重启**。

**要扩展到「所有 conf 文件」，成本极低**——同一个 `StrategyStore` 模式套上去即可。但目前 `configs/` 里真正生效的只有这一个文件，所以**没有实际可扩的对象**。

### 4.2 代码热插拔 ❌ **Windows 上不成立**

| 方案 | 结论 |
|---|---|
| Go 官方 `plugin` 包 | **Windows 不支持**（仅 Linux/macOS）。直接出局。 |
| C++ DLL 热替换（`FreeLibrary` + 重新 `LoadLibrary`) | Windows 会**锁定正在使用的 DLL 文件**，运行时无法覆盖；且需要「版本化文件名 + 原子指针切换 + 排空在途调用 + 永不 `FreeLibrary` 旧版本（只能泄漏）」——工程量远超收益，崩溃风险极高。 |
| 进程级换壳 | **已经是现状。** `net stop OKXWeb` → 覆盖 `bin\okxweb.exe` → `net start OKXWeb`，约 3 秒，且状态由 MySQL 持久化，中断无损失。 |

**结论：代码层不需要也不应该热插拔。** 真正要的是「改配置不重启」——这个已经有了。

### 4.3 进程级换壳 ✅ 已有，建议一键化

把「停三个服务 → 换 exe → 起三个服务 → 等端口」封装成一个 `redeploy.bat`，比任何 DLL 热插拔都安全。

## 五、真正该做的优化（按收益排序）

**这些才是「让它更快」的答案**——全部在 Go 里，全部几百行可完成。

### A. `refreshLatestKlines` 串行网络循环 → 并发（预计收益 40~140 倍）★最高优先级

**现状**（`internal/service/backfill.go:851`）：一个**串行 for 循环**遍历 479 个合约，每个合约**一次 OKX HTTP 请求**：

```go
for k, maxTs := range known {          // 479 个合约
    ...
    ks, err := m.feed.FetchCandles(instID, bar, 3)   // ← 每次 ~150ms 网络等待
    ...
}
```

15m K 线收盘的瞬间，**479 个合约同时到期** → 479 × 150ms ≈ **72 秒**（叠加限频退避/重试后就是实测的 **753 秒**）。

**修法**：套用 `scanner.go` 里已有的 worker pool 模式（`Workers=6`）→ 479 / 6 × 150ms ≈ **12 秒**。与 `syncTickers` 的 `max 10.75 s` 量级一致，说明这是可达的。

**预期**：`refreshLatest` 最大 753 s → **约 15~25 s（约 30~50 倍）**。

### B. 实时扫描改读本地 MySQL（预计收益 100 倍以上）★第二优先级

**现状**：库里已经有 **1,364,329 行** K 线，但 `scanner.go` 的实时扫描**完全不读库**，每轮对每个合约重新从 OKX 拉 400 根（2~3 次 HTTP）：

| 数据来源 | 单合约耗时 | 176 合约合计 |
|---|---|---|
| OKX REST（现状） | ~300 ms（2~3 次往返） | **~53 秒** |
| 本地 MySQL（`QueryKlines` 已存在） | ~1~5 ms | **~0.2~0.9 秒** |

`internal/repo/kline_repo.go` 的 `QueryKlines` / `LastKlineTs` **已经写好并且 `sigbackfill.go` 已经在用**——只是实时扫描这条路没接上。

**修法**：扫描先读本地库；只有「库里的最后一根落后于当前时间」时才去 OKX 补最新一根（这正是 `refreshLatestKlines` 的职责）。

### C. `ComputeSignal` 改成「一次算全序列」（修掉 O(n²) 隐患）

**现状**：为了判 `idx` **一根** K 线的信号，函数把 1500 根的**全部指标重算一遍**：

```go
h := make([]float64, n)   // ← n = 1500，每次调用都重新分配
l := make([]float64, n)
c := make([]float64, n)
v := make([]float64, n)
atrp14 := atrPercent(h, l, c, 14)   // 全部指标 × 全长
sma200 := sma(c, 200)
...
```

* 单次调用 **335.9 µs / 258 KB**，只为得到 1 根 K 线的判定；
* 逐根扫完整段就退化成 **O(n²)**：1500 根 = **440.6 ms / 361 MB**（实测）；
* 全市场逐根扫（479 × 1500）= **超过 3 分 39 秒仍未跑完**。

目前生产路径只用 tail（`idx = 最后一根`），所以**暂时没炸**；但 API 形状是坏的，任何「全历史回扫」需求一上来就会撞墙。

**修法**：拆成 `ComputeSeries(candles) []Signal`，指标只算一遍，之后 `O(1)` 取任意下标。**预计 tail 路径从 335 µs → 约 5~20 µs（20~60 倍）。**

### D. 消除 258 KB/次 的分配（GC 压力）

实测 `numGC = 9,443`（每秒 7.2 次），而 live heap 只有 3.5 MB —— 每秒产生的垃圾是本项目最大的「隐形税」。

**修法**：`sync.Pool` 复用 `h/l/c/v` 四个切片 + 复用一个 `Signal` 结构体；配合 §C 的「算一次」改造，分配次数可降到接近 0。

### E. 加一个 pprof 端点（先量再改）

目前**没有** `net/http/pprof`，所以「CPU 到底花在哪」只能靠纸面推断。加 5 行代码即可拿到火焰图——**在动任何优化之前先做这一步**。

## 六、如果一定要上 C++，唯一合理的范围

不建议全量重写，但**如果要试**，应该这样限定：

| 项 | 要求 |
|---|---|
| 范围 | **只包「指标计算」这一个纯函数**，不碰 I/O、不碰 DB、不碰 OKX 客户端 |
| 接口 | **批量**，不是逐根：`int compute_signals(const double* h, const double* l, const double* c, const double* v, int n, uint8_t* mask_out)` —— 输入输出都是裸指针，避免结构体跨边界 |
| 数据归属 | 缓冲区由 **C++ 侧持有**（避免每次 memcpy 60KB）；Go 只在配置文件热插拔时调一次 `refresh_history()` |
| 工具链 | 装 MinGW-w64，`CGO_ENABLED=1`，`-O3 -march=x86-64` |
| **验收门槛** | 先用 §五·C 把 Go 版做到 `ComputeSeries`，然后**基准对比**；若 C++ 版在 `bars1500` 上不能比 Go 版快 3 倍，直接放弃 |
| 预期收益 | 参考 §二：**整机提速 ≤ 0.14%**（因为计算只占 0.21%） |

**诚实提醒**：上表最后一行是这次评估最重要的数字。投入产出比在数量级上就不成立。
