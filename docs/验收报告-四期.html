一、SNDK 为什么亏了平仓 根因已定位

日志与库内双证（同一笔）

开仓  23:58:22  张数=0.001  开仓价=1744.30  共振 4/8  周期=3m
平仓  23:58:37  平仓价=1741.40  盈亏=-0.0033U(-0.17%)  原因=布林上轨（均值回归出场）
                       ↑ 相隔 15 秒

根因：布林上轨出场与买入判据读的是同一根 K 线

买入的硬条件之一是「触发那根 K 线必须真涨 > 1%」。那么同一根 K 线既然涨了 >1%， 它的 close 就有很大概率已经站在 SMA20 + 2σ 之上。 于是开仓之后，下一轮 3 秒巡检立刻判定「布林上轨」→ 反手市价平掉。

这不是偶发，而是结构性缺陷：买入条件越强（越要求「真涨」）， 越会命中布林上轨。两个条件在数学上互相拉扯。

处理

  • exit.boll_upper_exit ：true → false（关闭布林上轨出场）
  • 判决性证据：日志里最后一次 布林上轨（均值回归出场） 平仓是 00:36:04（HYPE），之后再未出现；超时 1 小时 到点自动平仓 成为唯一出场原因。

顺带澄清：全库没有任何「程序侧爆仓」记录

亏损最大的一批全部来自 OKX 历史同步（NMR -108.65 / ETH -103.41 / …）， 最近一笔 TIA -33.7 (-100.05%) 发生在 9/24 —— 都在本系统接管之前。

★ 下线周期会让「按仓位自己的周期加仓」永久静默失效 ★

加仓的 addon.rise_bar: "auto" 取的是仓位自己的周期（trade.bar）。 老仓可能是已经下线的 1m —— 那份 K 线会被 CleanupKlines 按 model.EnabledBars 整段删掉，于是 LatestSignal(…,"1m") 永远取不到数据。

后果不是「加仓条件略偏」，而是这个仓位再也不会加仓， 而且永久（K 线不会回来，重启/改回配置都没用）。

修法：service.addonBarFor 末尾再判一次白名单，不在名单就退回主周期，主周期也不在就取名单最后一个。

五、账户爆仓风险巡检（用户「不准爆仓」）

交易所强平不可关闭，只能量化 + 巡检。全仓 cross 下看的是账户整体： adjEq 跌破 mmr 才强平，与单个仓位的盈亏没有直接关系。

service.ProbeAccountDiag() 新增「爆仓风险巡检」段，可算出的指标：

  • 安全垫 = adjEq − mmr（> 0 就没爆仓，越厚越安全）
  • 名义敞口 ≈ Σ(imr × lever)
  • 安全垫 ÷ 名义敞口 = 「全部持仓同时反向跌多少 % 才吃光它」

★ 单币种保证金模式（acctLv=2）下顶层字段全是空串 ★

/account/balance 顶层的 adjEq / availEq / mmr 在这个模式下全部返回空字符串，真值在 details[USDT] 的 eqUsd / availEq / availBal / mmr。 不兜底就会整排显示 0 —— 看上去像「权益 0、随时爆仓」，比不显示更误导。

实测

占用保证金 2.64U（7.80%）

六、独立真实缺陷：补分区 DDL 从设计上就走不通 已修

原始写法（internal/repo/partition.go）

ALTER TABLE kline DROP PARTITION pmax, ADD PARTITION (...), ADD PARTITION (PARTITION pmax ...);
-- ❌ MySQL 不允许在同一条 ALTER 里既 DROP 又 ADD 分区，恒定报 Error 1064

也就是说这段代码从写下来那天起就没成功过：新分区永远补不上， 数据一路堆进 pmax —— 而 pmax 恰恰是「永不 DROP」的兜底分区， 于是容量只增不减。

它能潜伏这么久的原因是静默失败：只在日志里留一行 [WARN]， 对外表现（K 线照常入库、网页照常打开）与成功完全没有区别。

修法

ALTER TABLE kline REORGANIZE PARTITION pmax INTO (
  PARTITION pd20261004 VALUES LESS THAN (1791129600000),
  PARTITION pmax VALUES LESS THAN (MAXVALUE)
);
  • 一条语句、原子完成，中途不存在「没有兜底分区可写」的窗口。
  • pmax 正常情况下是空的（热区已铺到今天 + 2 天），本次 reorganize 不搬任何数据，代价≈0。
  • 拼装抽成纯函数 buildAppendPartitionDDL(table, parts, hasMax)， 新增 internal/repo/partition_append_test.go 钉死； 断言「绝不出现 DROP PARTITION」比断言「该出现的」更有价值。
  • 失败时把完整 DDL 一起打进日志（只打 Error 1064 等于什么都没说）。

判决性证据：换壳前后，同一条 SQL

01:18:10 [WARN] [PART] kline 补分区失败：Error 1064 (42000) ... near
                 'ADD PARTITION (PARTITION pd20261004 VALUES LESS THAN (1791129600000)), ADD PARTI' at line 1
                 ↑ 旧二进制（mb51）

01:19:59 [INFO] [PART] kline 新增分区：pd20261004
                 ↑ 新二进制（mb52），同一句 SQL，立即成功

分区数 14 → 15，pmax 仍在末位；pmax.ibd 实测仅 112 KB（是空的） → 该缺陷的最坏影响是「每日清理的 MaxDataLessThan 失真、偏保守」，未造成数据错误。
