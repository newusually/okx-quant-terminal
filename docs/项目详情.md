> 1. **括号块内部不能出现未转义的半角 `)`** —— `if (...)` / `for ... do (...)` 里任何一个裸 `)`
>    都会**提前闭合整个块**，后面的行全部变成 `xxx was unexpected at this time`。
>    实测两处：`echo ... %%ProgramFiles(x86)%% ...` 报「此时不应有 %\Git\cmd。」；
>    `git commit -m "auto(%TAG%): ..."` 报「) was unexpected」，症状是**代码仓永远提交不上**。
>    注意块内的 `echo` 文本也要守这条 —— 中文字典里的全角 `（）` 不受影响。
>    **最稳的改法是干脆不用括号块，改 `goto` 平铺。**
> 2. **`for /f` 的 `in('...')` 里不要给命令加引号** —— 触发 cmd 的「行首引号」陷阱，
>    报 `文件名、目录名或卷标语法不正确。` 且取到空值。绝对路径不加引号是安全的
>    （`%SystemRoot%` 展开后不含空格）。
> 3. **不要在管道之后判 `errorlevel`** —— `git push … | findstr …` 拿到的是 findstr 的退出码，
>    而 `findstr /v` 只要打出任意一行不含模式的内容就返回 0，于是**推送失败被报成「[OK] 已推送」**。
>    正确顺序：重定向到临时文件 → 立刻取 `errorlevel` → 再过滤打印 → 删文件。
>
> ⚠️ **git 不在系统 PATH**：这台机器唯一的 git 是 WorkBuddy 自带的 PortableGit
> （`%USERPROFILE%\.workbuddy\binaries\PortableGit\versions\1.2.0`）。
> **从 Git Bash 里调 `cmd` 会继承 bash 的 PATH，所以测不出这个问题** ——
> 必须用把 PATH 重置成 `C:\Windows\System32;C:\Windows` 的壳去跑才能复现
> （用户双击时就是这个处境，症状是 `'git' 不是内部或外部命令`，然后 add/commit/push 全挂）。
> `push_github.bat` 已内置探测并把找到的目录塞回 PATH。

## 三、架构分层

### 3.1 运行拓扑

```
浏览器
  │  http://<本机IP>/                    ← 对外只开 80
  ▼
Apache 2.4.68（Windows 服务 OKXApache）
  │  mod_proxy_http + mod_deflate         80 → 127.0.0.1:8090
  ▼
okxweb.exe（Go，只监听 127.0.0.1:8090）
  │
  ├── handler  接口层   HTTP ↔ 业务调用
  ├── service  业务层   准入 / 信号 / 交易 / 加仓 / 回补
  │     └── ml  计算层  纯 Go 神经网络
  └── repo     数据层   MySQL 仓储 + OKX SDK
  ▼
MySQL 8.0.43（Windows 服务 OKXMySQL，127.0.0.1:3306）
```

三层全部装在项目目录内（`mysql/`、`apache/`、`bin/`、`runtime/`），
不写注册表以外的系统目录，VC++ 运行库自包含。

### 3.2 依赖方向（严格单向，不允许反向）

```
        cmd/*  (可执行入口)
          │
          ▼
      handler ──────────┐
          │             │
          ▼             │
       service ─────────┤
       │     │          │
       │     ▼          │
       │    repo ───────┤
       │     │          │
       ▼     ▼          ▼
     model   conf     logx
```

**检验方法**：改 `handler` 的代码永远不会导致 `service` 编译失败。

### 3.3 各层职责边界（改代码时的判断标准）

| 层 | 可以做 | 不可以做 |
|---|---|---|
| **handler** | 解析 HTTP 参数、拼 JSON、调 service/repo、写响应 | 写 SQL、算指标、决定要不要下单 |
| **service** | 业务规则、信号计算、风控闸门、准入过滤、编排多个 repo | 直接写 `http.ResponseWriter`、直接 `sql.Open` |
| **repo** | SQL、DDL、外部 API 调用、文件读写 | 判断「信号够不够强」「该不该平仓」 |
| **model** | 定义字段和 JSON 标签 | 任何 IO、任何业务逻辑 |
| **conf / logx / perf / ratelimit** | 自身职责（配置、日志、计量、限速） | 反向依赖 service / handler / repo |

**跨层常量统一**：排除原因码定义在 `service/universe.go`（`ReasonStockETF` 等），
`cmd/okxweb` 只写码、`handler` 只翻文案 —— 两边永远不会漂移。

### 4.3 关键表结构

**`kline`** —— 写入量最大的表

```sql
CREATE TABLE kline (
  inst_id VARCHAR(32) NOT NULL,
  bar     VARCHAR(4)  NOT NULL,
  ts      BIGINT      NOT NULL,
  o/h/l/c/v DOUBLE NOT NULL DEFAULT 0,
  PRIMARY KEY (inst_id, bar, ts)
) ENGINE=InnoDB ROW_FORMAT=DYNAMIC
PARTITION BY RANGE COLUMNS(ts) ( ... );   -- 冷区按月 + 热区按周，共 20 个区
```

> **故意不加二级索引**：主键 `(inst_id, bar, ts)` 已是最优路径，
> 加一个二级索引多占约 70MB 且拖慢写入。

**`trade_event`** —— 交易明细

```sql
CREATE TABLE trade_event (
  id BIGINT AUTO_INCREMENT,
  inst_id VARCHAR(32) NOT NULL,
  kind    VARCHAR(12) NOT NULL,   -- open / addon / close
  ts      BIGINT NOT NULL,
  px, sz, margin, pnl, pnl_pct DOUBLE,
  leverage, score INT,
  reason VARCHAR(255), ord_id VARCHAR(64),
  trade_id BIGINT DEFAULT 0,
  created_at BIGINT,
  PRIMARY KEY (id),
  UNIQUE KEY uk_event (inst_id, kind, ts, trade_id),
  KEY ix_event_inst_ts (inst_id, ts),
  KEY ix_event_ts (ts)
);
```

> **唯一键为什么必须带 `trade_id`**：OKX 一笔大单会拆成多笔成交，
> 这些成交的 `fillTime` 经常落在同一毫秒。只用 `(inst_id, kind, ts)` 时，
> 同毫秒的后续成交会被 `ON DUPLICATE KEY UPDATE` 吃掉 ——
> 实测 100 笔成交只入库 49 条。程序自己产生的事件 `trade_id=0`，不受影响。

### 4.5 `kline` 分区方案

**冷区按月 + 热区按周（混合粒度）**

```
p_old      ← 兜底（所有早于冷区起点的行都落这里）
pm2024xx   ← 冷区，每月一个分区（历史数据到达时才生成）
...
pw20260801 ← 热区，每 7 天一个分区
pw20260808
...
pw20261128 ← 热区共 18 个周分区（覆盖约 4.5 个月）
pmax       ← 兜底（未来时间戳）
```

**实测分区清单**（2026-10-01，`information_schema.partitions`，共 **20** 个）：

```
p_old, pw20260801, pw20260808, pw20260815, pw20260822, pw20260829,
pw20260905, pw20260912, pw20260919, pw20260926, pw20261003, pw20261010,
pw20261017, pw20261024, pw20261031, pw20261107, pw20261114, pw20261121,
pw20261128, pmax
```

> **纯按月的致命问题**：9 月分区 402MB > `innodb_buffer_pool_size` 384MB，
> 一个月都装不下。
> **RANGE 分区不要求各分区等宽**，所以月粒度和周粒度能写在同一句
> `PARTITION BY RANGE COLUMNS(ts)` 里。
> 实测最大分区从 **402MB 降到 106.8MB**。

**分区裁剪验证**（`EXPLAIN`）：

```
partitions: pw20260912,pw20260919   type: range   key: PRIMARY   rows: 1344
```

> ⚠️ **`WHERE inst_id=?` 无法分区裁剪**（分区键是 `ts`）——
> 一条按 `inst_id` 的聚合 SQL 会扫全部 20 个分区。这是 CPU 事故的根因，见 [4.6](#46-性能红线)。

**分区 DDL 的坑**：
- `ALTER TABLE ... PARTITION BY` 是 `ALGORITHM=COPY` + `LOCK=SHARED`（禁写几分钟，必须停机）
- 421MB 表要 **75 秒**，而 DSN `readTimeout=60s` 到点直接掐断 → 需 `MySQLConfig.LongDDL=true` 把超时设 0
- 之后的 `ADD PARTITION` 在 MySQL 8 是 `INPLACE/LOCK=NONE`，可启动时自动补
- 生成分区子句**不能用 `--` 行注释**（会吃掉行尾逗号导致 1064），必须用 `/* */`

**★ 分区表最大的红利：删数据用 `DROP PARTITION`，不是 `DELETE`**

```sql
ALTER TABLE kline DROP PARTITION pw20260801, pw20260808, ...;
```

直接删数据文件，**毫秒级完成，不产生 undo / redo / binlog**。
相比之下 `DELETE FROM kline WHERE ts < ?` 要扫千万行，undo 日志会把 60GB 磁盘写爆 ——
年度级清理（1700 万行）用 `DELETE` 是**不可接受**的。这就是 `kline_retain_days = 365`
能落地的唯一原因。

选区判据**必须保守**（`internal/repo/kline_repo.go`）：

```go
for _, r := range parts {
    if r.IsMax || r.Name == partitionOldName { continue }  // p_old / pmax 永不 DROP
    if r.LessThan <= cutMs { hit = append(hit, r) }        // 上界 ≤ cutoff 才整段删
}
```

只有分区**上界 ≤ cutoff** 才代表该分区内**每一行**都过期；只要有一行没过期，整个分区就不能动。
只读验证（`cutoff = 2026-10-01`）：命中 `pw20260801`…`pw20260919`（8 个），
**`pw20260926`（上界覆盖到 10-03）被正确放过**；`cutoff = 2025-10-01` 返回 0 个。
`p_old` / `pmax` 无论 cutoff 多大多**永不 DROP** —— 删掉等于把不属于任何时间段的孤儿行连桶一起扔，
残余交给 `PurgeKlineBefore`（`DELETE … LIMIT 5000`，批间 20ms）兜底。

### 4.6 性能红线

这三条是 2026-10-01 CPU 事故换来的，**改代码时必须遵守**：

| 红线 | 原因 | 现在的做法 |
|---|---|---|
| **请求路径禁止 `COUNT(*)` 大表** | `COUNT(*) FROM kline` 单次 7.76 秒（分区后反而 11.9 秒） | `rowcount.go` 进程内缓存，TTL 10 分钟 |
| **禁止逐合约聚合** | `CoverageAll` 对 476 个合约各发一条 `GROUP BY bar`，每条扫 20 个分区，单请求 10~20 秒 | `coverage.go` 改成 1 条聚合 + SWR 缓存 + 单飞 |
| **禁止请求线程等 `information_schema`** | 该查询本身要 5.1 秒（要打开 data dictionary） | `tableMeta()` 冷路径不阻塞，CAS 踢后台刷新，自己返回合成值 |

**stale-while-revalidate 缓存策略**：

| 数据 | TTL | 预热 |
|---|---|---|
| 大表行数 | 10 分钟 | 启动后延迟 8 秒异步预热 |
| 表元数据 | 30 分钟 | 同上 |
| 全量覆盖情况 | 10 分钟 | 启动 +12 秒首次预热（避开写入高峰） |
| 单合约覆盖 | 20 秒 | 按需 |

**其他调优**：

| 项 | 值 | 说明 |
|---|---|---|
| `MaxOpenConns` | 16 | 2 核机器上每条连接 = 一个 OS 线程 |
| `MaxIdleConns` | 4 | 原来是 32，空闲连接太多 |
| `ConnMaxIdleTime` | 60 秒 | 原来是 5 分钟 |
| `innodb_buffer_pool_size` | 384MB | 2G 物理内存的保守值 |
| `innodb_flush_log_at_trx_commit` | 2 | 不每事务 fsync |
| `innodb_autoinc_lock_mode` | 2 | 交错自增锁 |
| `performance_schema` | OFF | 省 ~200MB |

**实测效果**：`/api/backfill` **10~20 秒 → 16 毫秒**；
MySQL 连接数 **55（52 Sleep）→ 19**；
慢查询日志里 `CoverageAll` 类聚合 **2237 → 0 条**。

### 5.2 关键接口参数

**`/api/mark`** —— K 线分页

```
GET /api/mark?inst=ETH-USDT-SWAP&bar=15m&limit=1000
GET /api/mark?inst=ETH-USDT-SWAP&bar=15m&limit=1000&before=1790495700000
```

响应含 `page` 元信息：`firstTs` / `lastTs` / `hasMore` / `earliestTs` / `totalBars`。

> **指标暖机**：`MA99` 需要前 98 根、布林需要前 19 根。做法是**多抓 99 根暖机段、
> 在原始序列上算指标、再把暖机段连同指标一起裁掉** —— 否则每页最前面 98 根没有均线，
> 翻页时会在缝上突然断掉。

**分页接口通用参数**：`size`（每页条数）、`page`（页码）、`days`（时间范围）

**`/api/events`** 额外支持 `kind=open|addon|close` 过滤。

> ⚠️ **表头统计必须用聚合 SQL 覆盖全部数据**（`ClosedTradesAgg` / `RecentEventsAgg`），
> 不能对当前页 reduce —— 否则翻页时「笔数 / 胜率 / 已实现盈亏」会变。

#### 6.1.1 MySQL 口令（2026-10-01 重构，与 OKX 密钥分开）

同一套「不落盘」的思路，但**走的是独立的解析链**（实现见 `internal/conf/secret.go`）：

| # | 来源 | 位置 | 说明 |
|---|---|---|---|
| 1 | **环境变量** | `OKX_MYSQL_PASS` / `OKX_MYSQL_USER` / `OKX_MYSQL_DSN` | 优先级最高。`OKX_MYSQL_DSN` 填了就整个覆盖前两个。**平时不该设**，见下 |
| 2 | **密钥文件** | 项目根 `.mysql-pass`（一行口令） | **唯一推荐来源**，Windows 服务实际读的就是它。已在 `.gitignore`。文件名常量 `conf.SecretFileMySQL` |
| 3 | 策略配置 | `configs/okx_strategy.json` 的 `store.password` | **建议留空**；留空时会自动落到 ①/② |
| 4 | 空 | — | 连不上时报错会直接打印去哪配（`MySQLHint()`），不再只说 `Access denied` |

> **为什么环境变量优先、却推荐用文件**：环境变量是 12-factor 的正统做法、不落盘；
> 但 Windows 服务的环境变量是 **SCM 在启动时整份拷贝**的，`setx /M` 之后已注册的服务
> 往往要重启整机才看得到。`.mysql-pass` 没有这个坑，所以 **OKXWeb 实际读的是文件**。
>
> ⚠️ **不要用 `setx` 把口令写进环境变量**（2026-10-01 修正）：不带 `/M` 的 `setx` 写的是
> **用户级**变量，明文躺在 `HKCU\Environment`，任何以本用户身份跑的进程 `printenv`
> 一下就能拿到 —— 等于把口令从 git 仓库挪进注册表，白改。而且它对 OKXWeb
> **完全无效**（服务跑 LocalSystem，读不到用户级变量）。所以 `set_db_pass.bat`
> **默认不再写环境变量**，要写必须显式加 `--env`。详见架构说明 §19.3.1。

```bat
rem 设置 / 轮换（双击也行）——  换完自动重启 OKXWeb
scripts\set_db_pass.bat --gen           :: 生成 24 位随机口令并轮换（推荐）
scripts\set_db_pass.bat                 :: 交互菜单（G 生成 / M 手工 / K 只写文件）
scripts\set_db_pass.bat --file-only     :: 只写密钥文件，不动 MySQL
scripts\set_db_pass.bat --env           :: 【不推荐】额外写用户级环境变量
```

清理已设过的用户级变量（`.NET` 置 `$null` 只会留空串，要真删用 `Remove-ItemProperty`）：

```powershell
[Environment]::SetEnvironmentVariable('OKX_MYSQL_PASS',$null,'User')
Remove-ItemProperty -Path 'HKCU:\Environment' -Name OKX_MYSQL_PASS -ErrorAction SilentlyContinue
```

**改代码 ≠ 堵住泄漏**。源码改成运行时解析只是让**以后**不再泄漏；历史提交里那把旧口令
（`OkxQuant****`，2026-10-01 已轮换失效）此前一直可用 —— 所以必须真轮换一次。
轮换不需要 MySQL root：`okx` 账号可以改自己的口令（`SET PASSWORD`）。

**自检**：`bin\okxweb.exe -init-only` 的横幅会打印实际生效的来源（**只打来源不打口令**），
例如 `口令来源 : 密钥文件 C:\...\finally\.mysql-pass`。

## 八、开发约定与环境坑

### 8.1 批处理编码约定

**所有 `.bat` 必须存为 `GBK(cp936) + CRLF`，且第 2 行写 `chcp 936`。**

原因：cmd.exe 是按**字节偏移**重读批处理文件的。若存成 UTF-8 又在文件里 `chcp 65001`，
代码页切换会让偏移错位，中文字节会把后面的 ASCII 吃掉，典型症状：

- `'lse' 不是内部或外部命令`（`else` 被啃掉）
- `'026'`（`2026` 被啃掉）
- `命令语法不正确`

存 GBK 时控制台代码页不变，偏移恒定，中文还能正常显示。

`.gitattributes` 已写死 `*.bat text eol=crlf`，防止克隆后变回 LF。
`.vbs` 同样需要转 GBK。

### 8.2 PATH 冲突与命令选择

装了 Git / Cygwin / MSYS 的机器，PATH 里会有同名的 GNU 工具，会和 Windows 命令打架：

| 不要用 | 改用 | 原因 |
|---|---|---|
| `find` | `%SystemRoot%\System32\findstr.exe` | GNU `find` 会报 `find: '-/I': No such file` |
| `timeout` | `ping -n 9 127.0.0.1` | `timeout` 在 stdin 被重定向时直接报错退出 |

### 8.3 本机特有坑

| 坑 | 现象 | 对策 |
|---|---|---|
| **`wmic.exe` 被黑名单** | `PROGRAM BLOCKED BY SECURITY POLICY` | 用 `typeperf.exe`（System32 签名程序）或进程内自测（`internal/perf`） |
| **PowerShell 被沙箱拒** | `__PSScriptPolicyTest_*.ps1` 被 block | 改用 bash + 文件 + 重定向 |
| **`go` 读不了 `Documents\**`** | `open ...: Access is denied`（同文件 `cp`/`Read` 正常） | 受控文件夹访问（CFA）拦第三方进程 → 把源码镜像到工作区再编译 |
| **`typeperf` 的 `_Total` 会误导** | `_Total` 恒 ≈ 200（= 忙 + 闲 = 总容量），**不代表满载** | 判断机器忙不忙必须看 `\Process(Idle)\% Processor Time` |
| **curl 测本机 HTTP** | 服务挂掉时 curl 要重试约 2 秒才返回 `Connection refused`，看起来像「每个请求都恰好 2.00 秒」 | 先用 `netstat` 确认端口在 LISTENING 再测 |
| **`tasklist /FI`** | Git Bash 会把 `/FI` 当路径转换 | 用 `tasklist \| grep` |
| **`/usr/bin/time` 不存在** | 计时失败 | 用 `date +%s%N` 算差值 |
| **`sc.exe` / `reg.exe` / `taskkill`** | 有时被程序黑名单拦 | 必要时改用 `net start/stop` |
| **服务被环境回收** | 三服务偶发全停（日志只有 `Normal shutdown`） | 把「启动 + 等端口 + 使用」串在**同一条命令**里，不要 `net start X; sleep N; 用 X` |

（库里要留够 1 年 K 线）—— 那是**算法口径**改动，不是语言问题。
