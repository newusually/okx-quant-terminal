3本轮新挖出的两个 bug（均已修复并实测）

bug ①  历史仓位同步的 lookback(35天) 与清理红线(30天) 不一致

后果是一个永久拉锯：30~35 天那一档的仓位，每 10 分钟被同步写入、 每周又被自动清理删掉，日志里 [CLEAN] trade 删了 88 行 反复出现，看着像一直没清干净。

const okxPositionsLookbackDays = 35   // ❌ 清理红线是 30 天

// ✅ 下界直接对齐保留窗口：多翻无收益，只会制造 churn
func okxPositionsLookbackDays() int { return repo.RetainDays() }

bug ②  OKX 翻页天然会多带一页

after=<毫秒> 的语义是「平仓时间早于该毫秒的下一批」， 所以「翻过下界就 break」这个判断必然发生在 append 之后 —— 每轮同步都会多带回一整页（最多 100 行，可横跨十几天）。

t := atoi64(ut)
if t > 0 && (oldest == 0 || t < oldest) { oldest = t }  // 游标先算
if sinceMs > 0 && t > 0 && t < sinceMs { continue }     // ★ 窗口外直接丢，不 append

5前端为什么不用改 HTML

周期按钮是数据驱动的 —— state.bars 来自后端 /api/state 的 bars 字段， 前端只负责遍历渲染。index.html 里只有一个空的 #tfGroup 容器，没有任何硬编码的周期按钮。

// web/assets/app.js
function renderTimeframes() {
  state.bars.forEach((b) => { /* 生成 .tf 按钮 */ });
}

所以「删除其它分钟数选项卡」＝ 改后端白名单 + 重新编译，不动 HTML。 验收：经 Apache 80 拉取的 app.js 与磁盘源文件一致， bars: ['15m']、BAR_MS = {'15m': 900e3}。

7结论

四条口径全部落地且经实测验收： ① 数据只留 30 天 —— trade / trade_event / equity / signals 超期行数均为 0； ② K 线、信号、买卖点只留 15m —— kline 表 bar 只剩一个值； ③ 前端只剩 15m 选项卡 —— /api/state 的 bars = ["15m"]，经 80 端口核验； ④ 清理周期保持每周一次 —— retainInterval = 7×24h。

附带修掉两个会导致「清完又长回来」的 bug（lookback 与红线不一致、OKX 翻页多带一页）， 并把清理单轮耗时从 30~100 秒降到 17.8 秒。

证据来源：curl /api/state · mysql.exe COUNT(*) · logs/okxbot.log · go vet / go test ./internal/... 全绿。 详细技术记录见 docs/架构说明.md §十七。
