# 架构说明（三层 + 分层职责）

> 本项目已从「一个 mvc.go 装下所有东西」重构为 **接口层 / 业务层 / 数据层** 三层结构。
> 所有 Python 文件已全部移除，后端 100% 纯 Go，不需要装 Python、不需要 CGO。
>
> **2026-09-30 重大变更**：存储从 SQLite 换成 **MySQL 8.0**（400+ 合约并发写，SQLite 单写者模型扛不住），
> 对外入口从「Go 直接监听」换成 **Apache 80 反向代理 → 127.0.0.1:8090**。

## 一、运行拓扑

```
浏览器
  │  http://<本机IP>/            ← 只开 80
  ▼
Apache 2.4.68 (Windows 服务 OKXApache, 自动启动)
  │  mod_proxy_http + mod_deflate   80 → 127.0.0.1:8090
  ▼
okxweb.exe (Go, 只监听 127.0.0.1:8090)
  │  接口层 handler + 业务层 service + 数据层 repo
  ▼
MySQL 8.0.43 (Windows 服务 OKXMySQL, 自动启动, 127.0.0.1:3306)
```

三层全部安装在 `C:\Users\Administrator\Documents\finally` 下（`mysql/`、`apache/`、`bin/`），
不写注册表以外的任何系统目录，VC++ 运行库自包含在 `runtime/` 与 `apache/bin/`。

## 三、依赖方向（严格单向，不允许反向）

```
        cmd/*  (接口层入口)
          │
          ▼
      handler  ──────────┐
          │              │
          ▼              │
       service ──────────┤
       │     │           │
       │     ▼           │
       │    repo ────────┤
       │     │           │
       ▼     ▼           ▼
     model   conf      logx
```

* `model` 谁都不依赖，只放结构体。
* `service` 不依赖 `handler`，`repo` 不依赖 `service`。检验方式：改 `handler` 的代码永远不会
  导致 `service` 编译失败。
* 排除原因码统一定义在 `service/universe.go`（`ReasonStockETF` 等常量）与 `service.ExcludeLabel()`，
  `cmd/okxweb` 只写码、`handler` 只翻文案，两边永远不会漂移。

## 四、各层职责边界（改代码时的判断标准）

| 层 | 可以做 | 不可以做 |
|---|---|---|
| **handler** | 解析 HTTP 参数、拼 JSON、调 service/repo、写响应 | 写 SQL、算指标、决定要不要下单 |
| **service** | 业务规则、信号计算、风控闸门、准入过滤、编排多个 repo | 直接写 `http.ResponseWriter`、直接 `sql.Open` |
| **repo** | SQL、DDL、外部 API 调用、文件读写 | 判断「信号够不够强」「该不该平仓」 |
| **model** | 定义字段和 JSON 标签 | 任何 IO、任何业务逻辑 |
| **conf / logx** | 配置与日志自身 | 反向依赖 service / handler / repo |

## 五、合约准入（「哪些合约能买」）

唯一判定处：`service.FilterUniverse()`。规则按顺序执行，先命中先出局。

| # | 规则 | 实现 | 排除码 |
|---|---|---|---|
| ~~1~~ | ~~不买美股 / ETF / 商品~~ **（三期已关闭）** | `instCategory != "1"`，受 `exclude_stock_etf` 控制（**当前 false**） | `stock_etf` / `commodity` / `category` |
| 2 | 不买刚上线的 | `listTime` 距今 < `exclude_new_listing_days`（默认 30 天） | `new_listing` |

| 4 | 24h 成交额下限 | `ticker.quote_vol24h < min_quote_volume_24h`（默认 100 万 U） | `low_volume` |
| 5 | 最小一手必须买得起 | `minSz × ctVal × ctMult × price ÷ lever ≤ max_order_margin_usdt` | `notional` |

> **★ 2026-10-02 三期：规则 1 默认关闭 ★** —— 用户口径「只要买入上限小于 1U 就做」，
> 品类不再是判据，唯一门槛是规则 5。放开后实测 **480 → 239**（此前 170）。
> 注意：**开关关掉不等于品类统计关掉** —— `ByCategory` 的计数必须留在 `if` 之外，
> 否则 `-universe` 诊断里的「分类分布」会变成一个空 map。

> **★ 规则 5 的上限 `max_order_margin_usdt` 完全由配置文件决定**（当前 **1.0U**，
> 2026-10-01 二期由 1.5U 收紧）。
> Go 里只留兜底默认值，真源永远在 `configs/okx_strategy.json`，
> 而且**改完即刻生效**（热插拔，见 §二十）—— 这正是「把可买入金额和 symbolList
> 做成可热插拔」的那条线。

> **★★ 准入策略只能有一个构造入口 ★★**
> `service.UniversePolicyFromConfig(cfg)` 是唯一正解。历史上 `Scan()` 手写过
> `UniversePolicy{...}` 漏填 `MarginPolicy`（准入上限静默 1U→0.01U，480→33），
> 三期又发现 `cmd/okxweb/main.go` 的 `applyUniverseFilter` 手写字面量漏填 `ExtraExclude`
> （手动黑名单 `exclude_inst` 只在下单扫描路径生效）。
> **新字段加进结构体和构造器，绝不会自动进手写字面量，编译器也不报错（缺字段 = 零值）**
> → `grep -rn "UniversePolicy{"` 必须全量收敛。

结论写回 `inst.tradeable` / `inst.exclude_reason`：

* **`tradeable` 只能由准入过滤写**。`UpsertInstruments` 的更新列里**故意不含**这两列——
  否则 10 分钟一轮的合约同步会把过滤结果冲回默认值 0（表现为「日志说 171 个可交易，
  网页列表一个都没有」）。
* 过滤有**两个触发源**：
  1. **每 30 分钟**兜底重跑（新币会老过 30 天、成交额会塌、公告会新出下线通知）；
  2. **配置文件一被改动**就立刻重跑（§二十 热插拔），所以改阈值不用等、更不用重启。
* 公告黑名单自身有 **24h 缓存**（落在 `meta.delist_blacklist`），重跑不会打爆 OKX 接口。
* 公告标题里出现 `postpone / delay / resume / cancel` 视为「撤销下线」，
  会把更早的下线公告从名单里撤掉（例：`ONE` 先公告下线、次日公告推迟 → 保留）。

## 六、加仓（★ 2026-10-02 三期：条件与买入仍是同一个判据函数）

口径：**加仓额 = 原持仓保证金 × 1/3**；
触发 = **与买入条件完全一致：`Score ≥ 3` 且触发那根 K 线涨跌幅 < -0.7%（严格小于，必须真跌）**。

| 项 | 口径 | 配置键 |
|---|---|---|
| 触发 | `SignalQualified(sig, 阈值, min_bar_rise_pct)`（同一个 `LatestSignal()`，与买入共用） | `addon.enabled` |
| 判定周期 | **按该仓位自己的周期**（3m 仓按 3m 判、15m 仓按 15m 判）；**周期已下线则退回主周期** | `addon.rise_bar: "auto"` |
| 补仓额 | 原保证金 × 1/3 | `addon.ratio: 0.3333` |
| 次数 | **不限** | `addon.max_times: 0` |
| 间隔 | 距上次加仓至少 N 根 | `addon.min_gap_bars` |

判定顺序（`service/addon.go` 的 `decideAddon()`，纯计算、可单测）：

1. 加仓开关开着
2. `LatestSignal(仓位周期)` 拿到了**已收盘**的当前信号（`sig.Ready`）
3. **`SignalQualified(sig, ThresholdFor(合约), MinBarRisePct())`** ——
   即 `sig.Score ≥ 阈值` **且** 涨跌幅过带符号门槛（> 0 必须真涨 / < 0 必须真跌，当前 -0.7）
4. 信号时间必须**晚于**开仓时间（同根 K 线不算）
5. 距上次加仓至少 `min_gap_bars` 根（按该周期时长换算毫秒）
6. `max_times > 0` 时检查次数上限；**`0 = 不限`**

> ★ **买入与加仓的共用与分道（七期 2026-10-02）★**
> 两处共用同一个 `LatestSignal()`（= `loadCandles` + `IndexOfLastClosed` + `ComputeSignal`）——
> 自己另取窗口会让递归指标的**种子位置不同 → 值不同**。
> 判据已分道：买入走 `SignalQualified`（score + 带符号涨跌幅门槛）；
> 加仓走纯价格条件（`sig.Close` 低于买入价 `addon.drop_pct`% 且 `sig.RisePct > addon.bar_rise_pct`%）。
> **共用部分必须继续共用**（同一根 K 线），**分道部分不许再混** —— 各写一半是最容易走岔的形态。

> ★ **`RisePct` 由谁填 ★**：`Signal.RisePct = (close − open) ÷ open × 100`，
> 由 `signalAt()`（整段实现）与 `computeSignalReference()`（参考实现）**两个实现都要填**，
> 并有单测逐值比对。`cur.O <= 0` 时保持 0 → 判为不合格（保守）。

> ★ **`rise_bar: "auto"` 的意义 ★**
> 老实现写死 15m —— 但二期三个周期都参与开仓，1m 开的仓如果按 15m 判加仓，
> 就是「用另一个周期的信号管这个仓位」。`auto` 让每个仓位按**自己的周期**判。
> 老仓（`trade.bar` 列为空）退回配置主周期。

> **`drop_pct` / 旧的「先跌 0.5% 后转涨」已废弃**：字段保留只为了读老配置不报错，
> 判定路径已经完全不看它。历史证据是 `closedWindow()`（`Candle.Confirm` 语义）
> 仍被 `addon_test.go` / `klines_confirm_test.go` 回归测试使用。

**加仓不新开持仓行**：`sz / entry_px(加权) / margin / addon_count / addon_margin / last_addon_ts`
就地合并进原行，所以出场判定与盈亏计算不用改也能按新均价生效。

## 七、K 线分页（七期：初始 100 根 + 左右双向翻页，每页 300 根）

前端一次只加载最新 **100 根**；鼠标**向左**滚到最前面自动再取更早的 **300 根**拼上去
（可一直翻到库里最早一根）；**向右**滚到最后面自动取更晚的 300 根（七期新增，
`after` 游标 + `Asc` 查询，渐进右移不跳段）。

### 接口

```
GET /api/mark?inst=ETH-USDT-SWAP&bar=15m&limit=100                → 最新 100 根
GET /api/mark?inst=ETH-USDT-SWAP&bar=15m&limit=300&before=TS      → TS 之前的 300 根（左移）
GET /api/mark?inst=ETH-USDT-SWAP&bar=15m&limit=300&after=TS       → TS 之后最早的 300 根（右移，七期）
```

响应里的 `page` 字段带翻页元信息：

| 字段 | 含义 |
|---|---|
| `firstTs` / `lastTs` | 本页最老 / 最新一根 |
| `hasMore` | 更早还有没有数据 |
| `earliestTs` | 库里该 (合约,周期) 的最老一根（翻到底了就停） |
| `totalBars` | 库里该 (合约,周期) 的总根数 |

### 关键实现：指标暖机

`MA99` 需要前 98 根、布林需要前 19 根。如果直接在「一页 1000 根」上算，
每页最前面 98 根就没有均线（表现为翻页后均线在缝上突然断掉）。

做法是 **多抓 99 根暖机段、在原始序列上算指标、再把暖机段连同指标一起裁掉**：

```go
const indicatorWarmup = 99
q := model.KlineQuery{InstID: inst, Bar: bar, Limit: limit + indicatorWarmup}
raw := db.QueryKlines(q)            // limit+99 根
pg.Raw, pg.Trim = raw, len(raw)-limit
pg.Rows = raw[pg.Trim:]             // 输出 limit 根
// 指标在 pg.Raw 上算，再按 pg.Trim 对齐吐出 → 每页都是完整均线点
//
// 七期右移（after 分支）同理：暖机 = after 之前最近的 99 根 +
// 主体 = after 之后**最早** limit 根（KlineQuery.Asc=true），Raw = 暖机+主体升序。
```

同理，**同一个 bar 的均线值在哪一页里算都一样**（只要那一页带着它的前 98 根），
所以前端可以把每页的 `ma7/ma25/ma99/boll*` 直接按 `ts` 合并，不需要重算。

### 前端

* `state.klines` 保存已加载的全部 K 线（升序），`state.ind` 保存指标序列。
* `mergeByTs()` 按 `ts` 去重合并 —— 翻页时往前拼，定时刷新时覆盖尾部。
* 往前插数据后，`setVisibleLogicalRange({from: lr.from + shift, ...})` 保持画面不跳。
* `subscribeVisibleLogicalRangeChange` → 可视区落到第 `PAGE_TRIGGER` 根之前就预加载。
* `scrollGuardUntil` 压住 `fitContent` 触发的那次回调，避免一打开就把所有历史页拉下来。

## 八、K 线保留策略（★ 2026-10-01 二期：三周期 · 10 天 · 每日清理）

保留窗口 = `store.kline_retain_days`（当前 **10 天**），覆盖周期 = `model.EnabledBars`
（`3m / 5m / 15m` 三个）。**权威名单只有这一份** ——
`/api/kline`、回补、信号回算、K 线清理**四处共用**。

| 周期 | 一天多少根 | 480 合约一天 | 10 天合计 |
|---|---|---|---|
| 3m | 480 | 23 万 | 230 万 |
| 5m | 288 | 13.8 万 | 138 万 |
| 15m | 96 | 4.6 万 | 46 万 |

> **1m 已于四期下线**（用户口径「取消 1 分钟买入条件和买入信号和选项卡和 K 线图」）。
> 它原本是行数成本的大头：一天 1440 根 ⇒ 480 合约 69 万行/天、10 天 690 万行，
> 独占全表约 2/3。下线后全库 K 线从 338 万行降到 87 万行。
| **合计** | | **约 110 万行/天** | **约 1100 万行** |

> 一期「只留 15m、留一年」是 1041 万行 —— 所以二期虽然恢复了三个短周期，
> 总行数并没有变多：窗口从 365 天砍到 10 天，砍掉的是 97%。

**删除走 `DROP PARTITION`**（`kline` 是 `RANGE COLUMNS(ts)` 分区表），
由每日任务在**凌晨 00:00~00:10** 跑一次：整段过期的**日分区**直接扔，
边界残余交给 `PurgeKlineBefore`（`DELETE … LIMIT 5000`，批间 20ms）。

> ★ **分区粒度必须细于删除粒度** ★ —— 热区因此从「按周」改成「按天」。
> 按周切时，永远有一个 7 天 / 90MB 的分区跨在 cutoff 上：既不能 DROP、
> 又必须逐行扫（`kline` 上**没有 ts 前缀索引**，主键是 `inst_id,bar,ts`），
> 每批 `LIMIT 5000` 都要重扫一遍 → 几十分钟。
> 按天切后边界分区只有 1 天，凌晨 00:0x 跑任务时 cutoff 恰好落在日边界附近。

**日分区边界必须对齐本地零点**（`dayStart()`）—— 锚在带时分秒的时刻上会让边界逐日漂移，
可 DROP 的天数一天比一天少（单测 `TestPlanBoundsDailyBoundariesAlignToLocalMidnight` 钉住）。

余量从「×6/5 + 2 天」收到「+1 天」：口径已经明确成「只保留最近 10 天」，多留就是白占磁盘。
回补侧同步用 `backfill.trimToWindow(cfg.Days)`，写入前就把超窗口的 K 线丢掉 ——
两边配合后「写进去又被删掉」的 churn 归零（详见 §十 之后）。

`CleanupKlines` 还会**顺手清掉不在白名单里的周期**（`SELECT DISTINCT bar` → 逐个整段删）：
1H/4H 这类不在册的周期，按「保留 N 根」的逻辑是永远删不掉的，只会白占磁盘。

**查询侧同步夹紧**：`/api/kline`、`/api/mark` 的 `days` 参数一律被
`handler.clampQueryDays()` 夹到 `kline_retain_days` 以内 —— 接口读不到库外的东西。

## 十四、OKX 历史仓位同步（2026-10-01 实测踩坑）

用户原话：「历史仓位根本不够看，这么多历史仓位只有 8 条记录」。
查下来**不是分页分少了，是分页参数用错了**。

### 14.1 `/account/positions-history` 的正确姿势

| 参数 | 实测结果 |
|---|---|
| `after=<posId>` | ❌ `{"code":"51000","msg":"Parameter after error"}` |
| `after=<毫秒时间戳>` | ✅ 返回**更早**的一批（语义 = 早于该毫秒） |
| `before=<posId>` / `before=<ms>` | ❌ `Parameter before error` |
| `begin` / `end` / `startTime` / `endTime` | ⚠️ **被静默忽略**：传 2026-04 的窗口，返回的还是最近那 100 条 |
| `limit=20` | ⚠️ 被忽略，**恒返回 100 条**（上限） |
| `type=1` | 返回 0 条 |
| `type=3` | ✅ 爆仓记录，覆盖 2024-12 起（和 type=2 是两个集合） |

网上大量示例写 `after=posId`，在这个接口上是**错的**。

### 14.2 `posId` 不是「一个仓位一个 ID」

OKX 按 **(合约, 方向, 保证金模式)** 分配 posId，平掉之后再开仓拿到的还是同一个。
实测 `ETH-USDT-SWAP` 一个 posId 底下挂了 **117 笔互不相干的交易**
（开仓价从 1718 到 2733 都有）。

所以幂等键必须是 **`posId` + 平仓时间(`uTime`)**（`repo.histKey`）。
只用 posId 当键 → 后一笔把前一笔覆盖，面板上永远只有 1 行 —— 这正是
「8 条记录」的另一半原因。

### 14.3 真实存量（2026-10-01 全量遍历）

| 口径 | 行数 | 唯一 posId | 跨度 |
|---|---|---|---|
| 不传 type | 6000+（60 页打满） | 560 | 2026-03-26 起 |
| type=3 爆仓 | 112 | 98 | 2024-12-09 起 |
| **最近 30 天** | **711** | **209** | — |

同步后本地 `trade` 表：**8 → 721 个已平仓仓位**（`[POSHIST]` 日志可自查）。
同步只往回取 35 天（`okxPositionsLookbackDays`），超过本地保留窗口的部分
由清理程序裁掉，没必要每次同步都拖 18 个月的数据。

> ⚠️ Windows 上从命令行拼 URL 时，命令替换出来的字符串尾部可能带 `\r`，
> 拼进去后 OKX 会**静默忽略非法参数并返回第一页** —— 表现是「翻页永远翻不动」。
> 所以所有出参统一走 `stringTrim()`。

## 十五、K 线「写进去又被删掉」的 churn（2026-10-01 修复）

### 症状
清理日志里 `kline` **每次稳定删 31,181 行、耗时 30~100 秒**，
而且删完几分钟又被写回来，无限循环。

### 根因（三段拼起来）
1. OKX `history-candles` 单次最多只给 **300 根**，而 300 根对不同周期是完全
   不同的跨度：5m = 1 天、15m = 3.1 天、1H = 12.5 天、**4H = 50 天**。
2. 回补把 300 根原样写库 → 4H 每个合约凭空多存 20 天数据（实测
   `max_cnt = 300`，正是那个 300）。
3. `CleanupKlines` 把 4H 裁到 `228 根 = 38 天` → 每次删 `(300-228)×479 ≈ 31,181` 行。

### 修法
* `backfill.trimToWindow()`：**写入前**丢掉 `ts < now - cfg.Days` 的 K 线。
* `CleanupKlines` 从 `trader` 的「每 20 轮」路径上摘掉 —— 它要 30~100 秒，
  挂在 20 分钟一次的路径上等于每 20 分钟把数据库按住两分钟
  （表现就是 K 线迟迟不更新、`live.exitPass` 从 3 秒涨到 26 秒）。
* 清理收敛成**一个入口**：`service.StartRetentionCleaner`，**一周一次**。

### 验收
| 指标 | 修复前 | 修复后 |
|---|---|---|
| 4H 行数 | 6 分钟内 104,797 → 135,978（反复） | 150 秒采样**恒为 104,797** |
| 清理删 K 线 | 每轮 31,181 行 | **0 行** |
| K 线裁剪触发点 | 3 处（trader 20 分钟 / backfill 6h / cleaner 6h） | 1 处（cleaner 每周） |

> 剩下的 72 秒耗时全部来自 1916 次「定位第 N 根」的 `ORDER BY ts DESC LIMIT 1 OFFSET ?`
> ——分区表没法用全局索引，每次要在 20 个分区上归并。
> 一周一次 → 占空比 0.012%，可以忽略。

## 十六、MySQL data 目录为什么“虚胖”（2026-10-01 排查）

用户问：「为什么 MySQL 的 data 目录那么大，是不是没删除干净？」

结论：**表数据删干净了，胖的是 binlog —— 而且是一行配置写错造成的。**

### 16.1 现场

| 目录 / 文件 | 占用 | 说明 |
|---|---|---|
| `OFF.000001` ~ `OFF.000023` + `OFF.index` | **3.27 GB** | 二进制日志（binlog） |
| `#innodb_redo/` | 193 MB | InnoDB redo |
| `undo_001` + `undo_002` | 302 MB | undo 表空间 |
| `okx/`（真正的表数据） | **200 MB** | 库内数据 131.6MB + 索引 |
| **合计** | **4.1 GB** | |

### 16.2 根因：`log_bin = OFF` 不是“关闭”

```ini
# conf/my.ini（错误写法）
log_bin = OFF
```

`log_bin` 是**接受文件名的选项**，MySQL 把 `OFF` 当成日志文件名 → 实际效果是：

```
log_bin          = ON
log_bin_basename = C:/.../data/OFF      ← 日志文件就叫 OFF
```

然后在 data 目录里默默攒 `OFF.000001 … OFF.000023`。
`binlog_expire_logs_seconds` 默认 30 天，所以几天的密集写入就堆到 3.6GB 也不会自己清。

这台机是**单实例、无主从复制、也不需要按时间点恢复**（K 线的源头是 OKX），
所以正确做法是彻底关掉：

```ini
# conf/my.ini（正确写法）
skip-log-bin          # 不是 log_bin = OFF
```

> 对比：`general_log = OFF` 是对的 —— `general_log` 是布尔变量，OFF 就是关。
> 踩坑的是 `log_bin` 这种「选项值为文件名」的变量。

### 16.3 一并收拾的另外两个

```ini
# 8.0.30+ 已废弃 innodb_log_file_size / innodb_log_files_in_group（只能用它们反推容量）
innodb_redo_log_capacity = 64M     # 原来按废弃参数算出 192M，2G 内存机器太奢侈
innodb_max_undo_log_size = 64M     # 配合 innodb_undo_log_truncate=ON 自动回收
```

### 16.4 处理与验收

1. 停 OKXWeb → 停 OKXMySQL
2. 改 `conf/my.ini`（`skip-log-bin` + redo/undo 两个上限）
3. 删掉 `mysql/data/OFF.*`（23 个 binlog + `OFF.index`）
4. 启 OKXMySQL → 启 OKXWeb

| 指标 | 处理前 | 处理后 |
|---|---|---|
| `mysql/data` | 4.1 GB | **676 MB** |
| `log_bin` / `log_bin_basename` | `ON` / `...\data\OFF` | **`OFF` / 空** |
| `#innodb_redo` | 193 MB | **65 MB** |

> ⚠️ 以后**不要**再把 `log-bin` 交给某个脚本去 append；
> 这个坑的隐蔽之处在于「配置看起来是对的、MySQL 也不报错、日志文件还正常在涨」。

## 十七、全库瘦身到「只留 15m · 只留 30 天」（2026-10-01）

> **★ 本节是一期的阶段记录，口径已被同日稍晚的二期覆盖 ★**
> 二期把周期恢复成 **3m/5m/15m 三个**、K 线窗口从 365 天改成 **10 天 + 每日清理**。
> 本节保留下来是因为里面的**手法**仍然有效（分区表不能按非分区键 DELETE、
> 前端选项卡由后端名单驱动、`TABLE_ROWS` 估算不可信等），
> 但**所有具体数字（行数、周期名单、保留窗口）请以 §八 和 §十八 为准**。

### 17.1 用户口径

> 「清除多余数据 只保留 30 天的数据，把 4H 1H 5m 全部删除，只保留 15 分钟的信号和买卖点；
>   选项卡删除其他分钟数；检查数据库是否还有其它数据，只保留应该保留的信号、买卖点、持仓、交易等信息。
>   每周清理一次不变。」

拆成四条：**① 数据只留 30 天 ② K 线/信号只留 15m ③ 前端只剩 15m 选项卡 ④ 清理周期 = 每周一次**。

### 17.2 为什么 `kline` 只能「重建表」而不能 `DELETE`

```sql
-- kline 是分区表：PARTITION BY RANGE COLUMNS(ts)
-- bar 不是分区键 → 下面这条要扫遍所有分区，无法分区裁剪
DELETE FROM kline WHERE bar <> '15m';   -- ❌ 全分区扫（1.9 亿行时代要跑十几分钟）
```

`bar` 虽然排在主键 `(inst_id, bar, ts)` 的第二位，但它**不是最左前缀**，
优化器用不上索引定位。所以整表瘦身走「建新表 + `INSERT SELECT` + `RENAME` + `DROP`」，
见 `scripts/sql/slim_to_15m.sql`。

> 反过来，**行数不多时**分批 `DELETE ... LIMIT 20000` 就够了 ——
> 本轮删旧 exe 遗留的 14.4 万行 5m（占全表 9.5%），7 批 + 1 尾批，秒级完成。

### 17.3 两处「写进去又被删掉」的新 churn

#### ① POSHIST 的 lookback 比清理红线多 5 天

```go
const okxPositionsLookbackDays = 35   // ❌ 清理红线是 30 天
```

后果是一个**永久拉锯**：30~35 天那一档的仓位，

```
每 10 分钟  POSHIST 同步写入  →  每周  PurgeExpired 删掉  →  再写入  →  再删 …
```

日志表现就是 `[CLEAN] trade 删了 88 行` 反复出现，看着像一直没清干净。

```go
// ✅ 下界直接对齐保留窗口：多翻无收益，只会制造 churn
func okxPositionsLookbackDays() int { return repo.RetainDays() }
```

**实测证据**（同一进程，只换了这行）：

| 同步时刻 | 覆盖范围起点 | 对应窗口 |
|---|---|---|
| 11:40:53 | `2026-08-27 14:07` | 35 天 ❌ |
| 11:44:00 | `2026-08-27 14:07` | 35 天 ❌ |
| **11:45:45** | **`2026-09-08 20:17`** | **30 天 ✅** |

#### ② OKX 翻页天然会多带一页

`after=<毫秒>` 的语义是「平仓时间**早于**该毫秒的下一批」，
所以「翻过下界就 `break`」这个判断**必然发生在 `append` 之后** ——
每轮同步都会多带回一整页（最多 100 行，可横跨十几天）。

```go
t := atoi64(ut)
if t > 0 && (oldest == 0 || t < oldest) { oldest = t }  // 游标先算
if sinceMs > 0 && t > 0 && t < sinceMs { continue }     // ★ 窗口外直接丢，不 append
```

### 17.4 前端选项卡是「数据驱动」的，不用改 HTML

周期按钮由 `state.bars` 渲染：

```js
// web/assets/app.js
function renderTimeframes() {
  state.bars.forEach((b) => { /* 生成 .tf 按钮 */ });
}
```

`state.bars` 来自后端 `/api/state` 的 `bars` 字段 →
**只要后端只报 `["15m"]`，前端就自动只剩一个选项卡**，

所以「删除其它分钟数选项卡」＝ 改后端白名单 + 重新编译，不动 HTML。

### 18.1 用户口径

第十七节的「只留 15m · 只留 30 天」是本轮的**起点**，用户在当天进一步改了口径：

> 用户口径：「只能查询保存最近 10 天数据，不能多，多出来就删除」+
> 「自动每天凌晨删除数据一次」。
> 于是新增 `RunDailyMaintenance`（每日任务）、热区从按周改按天、tick 从 30 分钟收到 10 分钟、
> K 线保留窗口 `kline_retain_days: 365 → 10`。

> 年度任务保留但基本空跑（每日任务已经把它做完了），留作「每日任务长期没跑」的兜底。

### 18.2 为什么是「三条独立红线」而不是一条

关键认识：**不同类型的行，增长速率差 3 个数量级**，塞进同一个窗口一定出事。

| 类别 | 代表表 / 对象 | 增速 | 保留窗口 | 由谁清 | 频率 |
|---|---|---|---|---|---|
| **K 线** | `kline`（3m/5m/15m 三周期） | 三周期合计约 **110 万行/天** → 10 天 ≈ **1100 万行** | `store.kline_retain_days = 10` | `RunDailyMaintenance` | **每日** |
| **记录表** | `trade` `trade_event` `signals` `equity` `runlog` `ai_call` `pnl_point` | `equity` **每 3 秒 1 条** → 留一年 = **1000 万行** | `store.retain_days = 30` | `RunRetentionCleanup` | **月度** |
| **日志文件** | `logs\*.log`、`logs\archive\**`、`logs\shots\**`、`apache\logs\*` | 几十 MB/天 | `store.log_retain_days = 30` | `purgeAllLogs` | **月度** |

一句话：**权益曲线留一年没意义（谁会看三个月前某 3 秒的浮盈），K 线窗口则由用户口径直接定死。**
（一期那句「K 线必须留一年，因为要拿来做回测」在二期被用户的口径覆盖了：
10 天窗口下想回测就只能靠 `archive/` 里的月度归档，或者重新从 OKX 拉。）
所以窗口必须拆开，不能共用一个 `retain_days`。

> 顺带修掉一个隐藏的语义混用：`backfill` 的 `cfg.Days` 和存储层的保留窗口是**两件事**。
> - `cfg.Days`（`-days 365`）= 回补时“往回想拉多远”
> - `repo.KlineRetainDays()`（`kline_retain_days = 365`）= “库里留多久”
>
> 第十七节的 `trimToWindow` 用的是 `cfg.Days`。如果保留窗口设 365、回补窗口还是 30，
> 那么刚拉回来的 300 天历史会被当成“超期数据”当场删掉 —— 白拉。
> 现已统一改为读 `repo.KlineRetainDays()`。

### 18.3 `kline` 是 RANGE COLUMNS 分区表 → 删数据应该 `DROP PARTITION`

第十七节§17.2 记过一个结论：`DELETE FROM kline WHERE ts < ?` 扫千万行是灾难。现在有了年份级红线，
这个问题必须正面解决 —— 而 `kline` 本来就是分区表：

| 分区名 | 含义 | 粒度 |
|---|---|---|
| `p_old` | 兜底垃圾桶（所有 `< 2026-09` 的历史） | 无 |
| `p202609` … | 冷区，落在一年以前的老月份 | **月** |
| `pw20260901` … | 热区，最近 8 周 | **周** |
| `pmax` | 兜底（未来时间戳） | 无 |

`ALTER TABLE kline DROP PARTITION pw20260801, ...` 是 **毫秒级**的：直接删数据文件，
**不产生 undo / redo / binlog**，也就不会像 `DELETE` 那样把 60GB 磁盘写爆。
一年级的清理用 `DELETE` 是**不可接受**的 —— 这就是要做分区删除的全部理由。

#### 选区规则（必须保守）

```go
// internal/repo/kline_repo.go
for _, r := range parts {
    if r.IsMax || r.Name == partitionOldName {   // pmax / p_old 永不删
        continue
    }
    if r.LessThan <= cutMs {                     // 上界 100% 落在 cutoff 之前
        hit = append(hit, r)
    }
}
```

「只有分区**上界 ≤ cutoff** 才整段 DROP」。直觉上看着保守，但它是**唯一正确**的判据：
上界 ≤ cutoff 才代表这个分区里**每一行**都过期；只要有一行没过期，整个分区就不能动。

只读验证（`cutoff = 2026-10-01`）：

```
命中：pw20260801 pw20260808 pw20260815 pw20260822 pw20260829
      pw20260905 pw20260912 pw20260919      ← 8 个，全部上界 ≤ 10-01
未命中：pw20260926（覆盖到 2026-10-03）       ← 正确放过
cutoff = 2025-10-01 → 0 个
```

`p_old` / `pmax` 无论 cutoff 多大多**永不 DROP** —— 它们是兜底桶，删掉等于把不属于任何
时间段的孤儿行连桶一起扔了。兜底交给 `PurgeKlineBefore(cutMs)`：

```sql
DELETE FROM kline WHERE ts < ? LIMIT 5000     -- 批间 time.Sleep(20ms)，上限 4000 轮
```

`dropKlineBefore(cutMs)` = 先 `DropKlinePartitionsBefore` 再 `PurgeKlineBefore`，两者都必须跑。

#### 18.3.1 补未来分区：**只能用 `REORGANIZE`**

`EnsurePartitions()` 每次启动都会把热区往前铺到「今天 + 2 天」。
问题在于**新分区必须插在 `pmax` 之前**，而 MySQL 不允许在 `MAXVALUE` 之后再加分区。
最初为此写成了一条「先 DROP pmax、再 ADD 新分区、最后把 pmax 加回来」的语句：

```sql
-- ❌ 从来没能执行成功过
ALTER TABLE kline DROP PARTITION pmax, ADD PARTITION (...), ADD PARTITION (PARTITION pmax ...);
```

**MySQL 不允许在同一条 `ALTER` 里既 `DROP` 又 `ADD` 分区**，恒定报 `Error 1064`。
而它的失败是**静默的**：只在日志里留一行 `[WARN] [PART] kline 补分区失败`，
对外表现是「服务正常、K 线照常入库」，直到容量出问题才会被发现 ——
实测这段代码**从写下来那天起就没成功过**，数据一路堆进 `pmax`，
而 `pmax` 恰恰是「永不 DROP」的兜底分区，于是容量只增不减。

正确形态是把 `pmax` 覆盖的那一段区间**原子地**拆成「若干新分区 + 新的 pmax」：

```sql
-- ✅ 一条语句、原子完成，中途不存在「没有兜底分区可写」的窗口
ALTER TABLE kline REORGANIZE PARTITION pmax INTO (
  PARTITION pd20261004 VALUES LESS THAN (1791129600000),
  PARTITION pmax VALUES LESS THAN (MAXVALUE)
);
```

`pmax` 正常情况下是空的（热区已经铺到今天 + 2 天），所以这次 reorganize
**不搬任何数据，代价≈0**。实测证据（同一条 SQL，换壳前后）：

```
01:18:10 [WARN] [PART] kline 补分区失败：Error 1064 ... near 'ADD PARTITION (PARTITION pd20261004 ...'
01:19:59 [INFO] [PART] kline 新增分区：pd20261004          ← 换壳后立刻成功
```

DDL 的拼装抽成了纯函数 `buildAppendPartitionDDL(table, parts, hasMax)`，
由 `internal/repo/partition_append_test.go` 钉死 —— 这条 SQL 坏过一次，不能再靠「跑起来试试」。

### 18.4 调度：用 meta 表记「上次跑的月份」而不是定时器

**不能用 Windows 计划任务** —— 这台机器上 `schtasks.exe` 被安全策略拦掉（实测）。
也不能用 Go 的 `time.Ticker` 直接算「月底」：机器会重启、服务会被拉停，
「月底那一刻进程恰好活着」是不保证的。

所以做成 **幂等 + 月/年粒度**：

```go
const (
    maintTickInterval = 30 * time.Minute   // 30 分钟比对一次
    maintFirstDelay   = 90 * time.Second   // 启动 90 秒后才开始，别抢启动资源
    metaLastMonthly   = "maint_last_monthly"
    metaLastYearly    = "maint_last_yearly"
)
```

`RunDueMaintenance()` 每次 tick 读 meta 里的 `maint_last_monthly`，
和 `now.Format("2006-01")` 比对，**不同才跑**，跑完写回当前月份。

好处：**停机三天、重启二十次，这个月的任务也只跑一次 —— 不重不漏。**
首次部署时把 `maint_last_monthly` 种子化为当月（`2026-10`），
所以**部署瞬间不会触发真实的回收站清理**，第一次真实月度任务落在 11-01。

```go
// 本质就这几行
if meta[metaLastMonthly] == now.Format("2006-01") {
    return  // 本月已跑过
}
runMonthly()
meta[metaLastMonthly] = now.Format("2006-01")
```

### 18.5 月度任务的 6 步顺序 —— **推送必须在磁盘守卫之前**

```
① 归档所有「还没归档过」的、早于本月的月份
   → archive/kline-<周期>-YYYY-MM.partNN.csv.gz + manifest-YYYY-MM.json
     ★ 二期：三个周期（3m/5m/15m）各一组分片；
       「已归档」的判据从「manifest 在不在」升级为「逐周期核对」
       （老清单只有 15m，缺 1m/3m/5m → 判为未完成 → 重导覆盖）
② 推送 GitHub（数据仓）        ← ★ 必须在 ⑤ 之前 ★
③ 记录表清理（30 天）
④ 日志清理（30 天，DB + apache + 客户端）
⑤ 磁盘守卫（C 盘 < 10 GB → 只留当月；含 K 线侧与归档侧两个动作）
⑥ 清回收站
```

**★ 每日任务（二期新增，只做 K 线一件事）★**

```
cut = now − kline_retain_days（10 天）
① DROP PARTITION（整段过期的**日分区**，毫秒级）
② PurgeKlineBefore（边界残余，DELETE … LIMIT 5000，批间 20ms）
```

调度与月度/年度完全一致（meta 记「上次跑的哪一天」），
**每日失败只记 WARN 不 return** —— 不能拖累窗口长得多的月度/年度任务。

#### ① 为什么是「补齐式」而不是「只导上个月」

最初写的是「导出上个月」，看起来够用 —— 每月跑一次，每个月的数据在下个月被导走。
**但它和 ⑤ 撞在一起会丢数据**：

> ⑤ 会把 K 线收缩到「只留当月」。如果某个早于当月的月份**从来没见过归档文件**，
> 那一刀下去就是永久损失 —— 库里删了、远端也没有。

什么时候会出现「缺口月份」？**首次部署**（库里已经有几个月历史数据）、
**停机几个月**、**上一次导出失败**。这三种情况在真实运维里都会发生。

本轮实测就撞上了：1 年回补正在慢慢把历史拉进来，`-maint-dry` 立刻报出
**12 个待归档月份**（2025-10 ~ 2026-08）。如果沿用「只导上个月」，
这 12 个月里除了 2026-09 之外，全部会在 ⑤ 触发时被无声删掉。

所以 ① 改成：取 `repo.KlineMonths()`（库里实际存在的月份），
**逐个检查是否已有归档，缺哪个月补哪个月**。天然幂等 —— 判据是
`manifest-<YYYY-MM>.json` 是否存在（它是 `ExportMonth` 跑完后由 `WriteManifest`
最后写出的文件，所以「manifest 在」就等于「那个月导出完整」；
只有 `.gz` 没有 manifest 说明上次中途挂了，下一轮会重导并覆盖同名分片）。

```
早已归档   : 2026-09（跳过，不重复导出）
待归档月份 : 2025-10, 2025-11, 2025-12, 2026-01, 2026-02, 2026-03,
             2026-04, 2026-05, 2026-06, 2026-07, 2026-08      ← 真实输出
```

#### ② 为什么必须在 ⑤ 之前

⑤ 有两个破坏性动作：删库里早于收缩点的 K 线，以及删本地 `archive/` 里早于当月的归档。
后者删完本地就只剩远端那一份了。所以**先推后删**：
最坏情况（推送失败）只是「本地多占一点磁盘」，而不是「数据永久丢失」。
反过来先删后推，一旦推送失败（断网 / token 过期 / 数据仓被删）就是双份丢失。

#### ② 失败时的门禁不是「全停」，而是精确地关掉「删本地归档」

推送失败时记 `rep.PushErr` 并打一条 WARN，然后：

| 第 ⑤ 步的动作 | 推送成功 | 推送失败 |
|---|---|---|
| 删库里早于收缩点的 K 线 | 执行 | 执行，但**收缩点回退**到第一个未归档月份（见下） |
| 删本地 `archive/` 里早于当月的归档 | 执行 | **跳过** —— 本地 `archive/` 是唯一副本 |

收缩点回退是一个额外的保险：⑤ 的目标是「只留当月」（`cut = 本月月初`），
但从本月往回走，只要撞到第一个「有数据但没归档」的月份，就把收缩点挪到那个月的月初 ——
**没归档的月份，一行都不删**。正常情况下所有历史月份都已归档，这个回退不会生效，
收缩点就是本月月初，和用户口径完全一致。

> 实测这段逻辑的意义：库里 2025-10 ~ 2026-08 共 12 个月还没归档时，
> 若 ⑤ 在此时触发，收缩点会从 `2026-10-01` 一路回退到 `2025-10-01`（什么都不删），
> 而不是把 12 个月全部删光。

归档侧的判据 `PruneArchivesBefore(dir, keepYM, dryRun)` 认两种文件名
（`kline-<bar>-<YYYY>-<MM>.partNN.csv.gz` / `manifest-<YYYY-MM>.json`），
解析出来的 `YYYY-MM` 是定宽零填充，所以**字符串比较 == 时间比较**，
`ym >= keepYM` 就是「当月或未来」，直接跳过。**识别不出来的文件名一律不动**
—— 目录里将来可能被塞进 README、校验脚本之类的东西，宁可漏删不能误删。

这一段在磁盘充足时线上永远跑不到，而它一旦判错就是删掉唯一副本，
所以单独写了单测钉死（`internal/service/archive_prune_test.go`，4 个用例：

```

--- PASS: TestPruneArchivesBeforeMissingDir  目录不存在不是错误
```

### 18.6 归档格式：为什么按「压缩后字节」滚动分片

**GitHub 单文件硬上限 100 MB**。经验值是「每片 20 万行」，但这是**魔数**：
不同月份的行数、币价精度不同，压缩比能差 3 倍（1.33M 行 → 17.4 MB，也可能同样是
1.33M 行 → 90 MB）。**押行数就是在赌**。

所以按 **压缩后字节数** 滚动，`archiveChunkBytes = 40 << 20`（40 MB）留足余量：

```go
if cw.n >= archiveChunkBytes {   // countingWriter 统计的是 gzip 之后、落盘的真实字节
    sealPart(); openPart(next)
}
```

`countingWriter` 包在 `gzip.Writer` **下面**（即最靠近文件的那一层），
所以它数出来的就是文件真实大小，不是 CSV 行宽估算。

#### ★ 收尾顺序绝对不能反 ★

```go
// sealPart 闭包：先 flush + close，再统计行数/字节/哈希
sealPart := func() error {
    csvw.Flush()                    // ① 吐出 CSV 缓冲里最后不到 2 万行
    if err := csvw.Error(); err != nil { ... }
    gz.Close()                      // ② 补写 gzip 尾部 8 字节（CRC32 + 原始长度）
    file.Close()                    // ③ 真正落盘
    part.Rows   = partRows          // ④ 这时候统计才是对的
    part.Bytes  = cw.n
    part.Sha256 = hex.EncodeToString(hash.Sum(nil))
    ...
}
```

踩过的坑：最初在 `gz.Close()` **之前**统计 → 清单里少算了 **22,649 字节**，
`sha256` 和实际文件对不上 → 校验必然失败。这两步（CSV 缓冲残留、gzip 尾部）
只在 close 之后才存在于文件里。

#### 清单（manifest）与校验

`manifest-YYYY-MM.json` 记录 `month / bar / source / from / to / insts / totalRows /
totalBytes / columns / tsUnit / parts[]`，每个 part 带自己的 `name / rows / bytes / sha256`。

实测（2026-09）：

```
kline-15m-2026-09.part01.csv.gz   18,293,379 字节
rows  1,336,768      合约 479      耗时 27 秒      分片 1 个
sha256 e9952ff5e7a583ce…   ← 重新计算后与清单完全一致
gzip -t 通过 / CSV 表头正确
```

注意 `tsUnit` 字段：`ts` 存的是**毫秒**。而 CSV 里用 `f2s`
（`strconv.FormatFloat(v,'f',-1,64)`）而不是 `%.2f` —— 否则小币价会全部写成 `0.00`，
回滚数据直接报废。

### 18.7 磁盘守卫：C 盘 < 10 GB 时「只留当月」

```go
if rep.FreeGBBefore < float64(repo.ArchiveMinFreeGB()) {   // 默认 10 GB
    // ① K 线侧：DROP 掉早于收缩点的分区（收缩点默认 = 本月月初）
    // ② 归档侧：删掉 archive/ 下早于当月的 .gz 与 manifest（需推送成功）
}
```

只判 C 盘（系统盘就是数据盘就是归档盘，这台机器只有 60 GB，没有多盘可言）。
阈值可配置；`disable_recycle_clean` 与它无关，各自独立。

收缩点在两种情况会偏离「本月月初」：

* **有未归档月份** → 回退到第一个未归档月份的月初（宁可多占磁盘，不能删唯一副本）
* `-maint-dry` 预演 → 只报告、不执行（`GuardKeepYM` 会照实打出来）

K 线侧走的是 `dropKlineBefore(cut)`，即「先 `DROP PARTITION` 再 `DELETE` 兜底」，
和年度任务同一套代码（见 [4.5](#45-kline-分区方案)）。

### 18.8 回收站：为什么不能用 `SHEmptyRecycleBin`

直觉做法是 Windows Shell API `SHEmptyRecycleBin(NULL, NULL, SHERB_NOCONFIRMATION)`。
**在这台机器上它是坏的**，原因有两层：

1. **Session 0 / LocalSystem**：`okxweb` 是 Windows 服务，跑在 `Session 0`，
   身份是 `LocalSystem`。`SHEmptyRecycleBin` 清的是**调用者自己那份**回收站 ——
   也就是 SYSTEM 的空回收站，清完什么都没发生。
2. **回收站是按用户隔离的**：文件实体在 `C:\$Recycle.Bin\<SID>\` 下，
   每个用户一个 SID 目录。你真要清的是 `Administrator` 那份，SYSTEM 看不到。

所以直接走文件系统：遍历 `C:\$Recycle.Bin` 下**形如 SID 的目录**
（`isSIDDir`：`S-1-` 前缀 + 只含数字和 `-`），逐个 `WalkDir` 删文件，
再**第二遍自下而上删空目录**（顺序反了删不掉）。

```go
RecycleBinRoot = `C:\$Recycle.Bin`   // recycle_windows.go
// 结果结构
type RecycleResult struct { Roots, Items, Bytes, Dirs, Skipped int; DryRun bool; Err string }
```

权限不足时 `res.Skipped++` 并**继续**，不中断整轮清理 —— 别的用户目录删不掉不该拖垮全流程。

> 这个操作**不可逆**，所以配了反向开关 `store.disable_recycle_clean`（默认 `false` = 清）。
> 想保留就直接改成 `true`。
>
> 预演实测：**5,686 个文件 / 287.1 MB / 0 个目录 / 跳过 0 项**，耗时 331 ms。

### 18.11 GitHub 推送脚本

`scripts\push_github.bat`，用法 `push_github.bat [code|data|check]`：

| 模式 | 动作 |
|---|---|
| `check` | 只打印远端连通性与待推送提交数，不推 |
| `code` | 推代码仓 `github.com/newusually/okx-quant-terminal.git` |
| `data` | 推数据仓 `github.com/newusually/okx-quant-terminal-data.git`（`archive/` 是独立 git 仓库） |

凭据优先级：`%ROOT%\.git-token`（一行 PAT）→ `%GITHUB_TOKEN%` 环境变量。
**都没有则 `exit /b 2` 干净退出，绝不卡在交互式用户名提示上** —— 服务里跑的命令，
一旦卡在提示符上就是永久挂起，所以 `cmd.Env` 里强制注入：

```
GIT_TERMINAL_PROMPT=0
GCM_INTERACTIVE=never
```

推送用**带 token 的临时 URL**，不写进 `.git/config`：

```
git push "https://x-access-token:%TOKEN%@%REPO%" HEAD:%BRANCH%
```

这样 `.git/config` 里不会留下凭据明文，`.git-token` 也已在 `.gitignore` 里。

调用侧（`cleanup.go`）：

```go
exec.CommandContext(ctx, "cmd", "/c", bat, what)   // 15 分钟超时
```

#### 用假 token 实跑才发现的三个真缺陷

写完之后拿一个假 token 真跑了一次 `push_github.bat code`，暴露三个都不是理论问题的 bug：

**B1 推送失败被报成「[OK] 已推送」**（最严重）

原写法：

```bat
git push "https://x-access-token:%TOKEN%@%REPO%" HEAD:%BRANCH% 2>&1 | findstr /v "x-access-token"
if errorlevel 1 ( echo [X] 推送失败 & exit /b 1 )
```

管道里的 `%ERRORLEVEL%` 是**最后一个命令**（`findstr`）的，不是 git 的。
而 `findstr /v` 只要打出任意一行不含模式的内容就返回 0 ——
推送失败时 git 的错误信息恰好全属于这类。实测输出：

```
remote: Invalid username or token. Password authentication is not supported for Git operations.
fatal: Authentication failed for 'https://github.com/newusually/okx-quant-terminal.git/'
[OK] code 已推送到 github.com/newusually/okx-quant-terminal.git (master)   ← 假的成功
```

后果很严重：`cleanup.go` 靠退出码判断要不要跳过「删本地归档」，
而这个脚本永远返回 0 —— 门禁等于不存在。
修法：**先重定向到临时文件 → 立刻取 git 退出码 → 再过滤打印**（过滤是为了
万一 git 把带 token 的 URL 回显进输出）→ 删临时文件。
过滤与删文件都放在取完退出码之后，绝不让管道污染 `errorlevel`。

**B2 分支名永远取到空串**

```bat
for /f "tokens=2" %%B in ('git rev-parse --abbrev-ref HEAD 2^>nul') do set "BRANCH=%%B"
```

`--abbrev-ref HEAD` 只输出**一行**分支名（1 个 token），`tokens=2` 取到空串。
实测：`[tokens=2] -> []` / `[tokens=1] -> [master]`。
也就是说 `BRANCH` 一直是靠下一行 hardcode 的 `if not defined BRANCH set "BRANCH=master"`
兜底蒙对的；仓库改名 `main` 之后会静默推到错误的分支名。
改为 `git symbolic-ref --short HEAD`（整行取，`delims=`），
再退到 `rev-parse` 的 `tokens=1`，最后才兜底。

**B3 自动提交的日期带斜杠和星期**

中文 Windows 的 `%DATE%` 是 `2026/10/01 周四`，原样拼进提交信息得到
`auto(code): 2026/10/01 周四 12:58:26.78` —— 既难看也无法按字符串排序。
复用文件里已有的 `tokens=1-3 delims=/ ` 技巧拼成 `YYYY-MM-DD HH:MM`。

另外 `call :pushone` 的失败此前不传递（`:pushone` 里 `exit /b 1` 之后外层继续跑，
最后无条件 `exit /b 0`），现用 `FAILED` 标记累积，`:done` 按标记返回退出码 1。

验证（真实退出码）：

```
假 token → [X] code 推送失败（git 退出码 128） → bat 退出码 1
无 token → [X] 找不到 GitHub 凭据             → bat 退出码 2（绝不卡交互提示）
```

## 十九、MySQL 口令保密：从「硬编码」到「运行时解析 + 真轮换」（2026-10-01）

### 19.1 事件

旧口令曾经硬编码在 **7 个入库文件**里：

| # | 文件 | 形态 |
|---|---|---|
| 1 | `cmd/okxweb/main.go` | `flag.String("mysql-pass", "<明文>", ...)` |
| 2 | `cmd/okxbench/main.go` | 同上 |
| 3 | `internal/repo/mysql.go` | `DefaultMySQLConfig()` 的 `Password` 字段 |
| 4 | `internal/conf/config.go` | `defaultConfig()` 的 `Store.Password` 字段 |
| 5 | `scripts/install_services.bat` | `CREATE USER ... BY '<明文>'` |
| 6 | `scripts/sql/init_db.sql` | 同上（手工兜底脚本） |
| 7 | `scripts/start_all.bat` | `mysqladmin -uokx -p<明文> ping` |

而仓库是 **public** 的 —— 等于这把口令连同代码一起公开了。

> 「只监听 127.0.0.1，风险低」这个判断本身不算错，但它挡的是外网，
> 挡不住本机的任何进程。风险不该由「恰好没人翻仓库」来兜。

### 19.2 ★ 改代码 ≠ 堵住泄漏 ★（本轮最重要的一条）

把源码改成「运行时读环境变量」只解决**未来**：历史提交 `d21f976` 里那把旧口令
**至今仍然有效**，克隆仓库的人照样能连上来。

所以本轮做了两件事，缺一不可：

1. 源码 / 脚本里不再出现任何明文口令（19.3）
2. **真的把口令换掉** —— `scripts\set_db_pass.bat --gen`，旧口令从此 `Access denied`（19.6）

只做第 1 件是最容易交付、也最没有用的那种「安全修复」。

### 19.3 解析链（`internal/conf/secret.go`）

```
① 环境变量  OKX_MYSQL_PASS  /  OKX_MYSQL_USER  /  OKX_MYSQL_DSN
② 密钥文件  <项目根>\.mysql-pass    （第一行；已在 .gitignore）
③ 空        →  连不上时报错直接说去哪配（MySQLHint）
```

为什么环境变量优先、却仍然推荐文件：

* 环境变量是 12-factor 的正统做法，不落盘、进程内可见；
* 但 **Windows 服务的环境变量是 SCM 在启动时整份拷贝的**，`setx /M` 之后
  已注册的服务往往要重启整机才看得到。`.mysql-pass` 没有这个坑；
* 结论：**OKXWeb 服务实际读的是文件**。两个 bat helper 的读取顺序必须与这里
  **严格对齐** —— 不一致就会出现「服务连得上、脚本连不上」这种鬼问题。

细节：`readSecretLine()` 会吃掉 UTF-8 BOM 和 CRLF。用记事本存出来的密钥文件经常带
这两样，而带着 BOM 的口令会直接认证失败，现象是「密码明明没错却连不上」。

#### 19.3.1 反面教材：别把口令留在环境变量里（2026-10-01 修正）

第一版 `set_db_pass.bat` 默认会 `setx OKX_MYSQL_PASS "<口令>"`。**不带 `/M` 的 `setx`
写的是用户级变量**，明文落在 `HKCU\Environment`。实测：

```
[Environment]::GetEnvironmentVariable('OKX_MYSQL_PASS','User')     -> 6Awr7wQxYH8fMZiRLgcFijDS
[Environment]::GetEnvironmentVariable('OKX_MYSQL_PASS','Machine')  -> (空)
printenv OKX_MYSQL_PASS                                            -> 6Awr7wQxYH8fMZiRLgcFijDS
```

两个问题：

1. **任何以该用户身份运行的进程都能拿到明文**（上面第三行就是在 Git Bash 里
   `printenv` 出来的）。这等于把口令从「git 历史」挪进了「注册表」——**白改**。
2. **它对 OKXWeb 服务完全无效**：服务跑在 LocalSystem，读不到用户级变量，
   实际读的还是 `.mysql-pass`。所以那个环境变量是**纯冗余暴露面**，唯一价值是
   新开 cmd 窗口手敲 `mysql` 时省一次翻文件。

修正后的口径：

* `set_db_pass.bat` **默认不再写环境变量**（`DO_ENV=0`）；要写必须显式加 `--env`，
  且会先打印一段风险说明。`--no-env` 保留（现在等于默认值，兼容旧写法）。
* 只留 `.mysql-pass` 一条路 —— 文件有 ACL + `.gitignore` 双保护。
* 清理已经设过的用户级变量：

```powershell
[Environment]::SetEnvironmentVariable('OKX_MYSQL_PASS',$null,'User')
Remove-ItemProperty -Path 'HKCU:\Environment' -Name OKX_MYSQL_PASS -ErrorAction SilentlyContinue
```

> 注意第二条：`.NET` 的 `SetEnvironmentVariable(...,$null,'User')` 在注册表里留下的是
> **空字符串值**（`len=0`），不是删除该项。想真正删干净要用 `Remove-ItemProperty`。
> 空值危害不大，但会让「查注册表还以为设着」这种误判发生。

### 19.4 ★ 真正会咬人的地方：flag 默认值会压掉一切 ★

只把 `secret.go` 写好是**不够的**。改动前的代码是：

```go
mPass = flag.String("mysql-pass", "<明文>", "MySQL 密码")          // 默认值 = 明文
...
mcfg.User, mcfg.Password, mcfg.Database = *mUser, *mPass, *mDB    // 无条件赋值
```

第二行**无条件**把 flag 值写进配置 —— 而 flag 默认值永远非空，于是它
**永远压过**环境变量、压过密钥文件、也压过 `configs/okx_strategy.json`。
把口令从源码里删干净、在 `secret.go` 里做得再讲究，这一行不改就是**完全没生效**。

改法（`cmd/okxweb/main.go` 的 `applyMySQLFlags`）：空串 / 0 一律解释成「没传」，
保留 `DefaultMySQLConfig()` 已经解析出来的值。`cmd/okxbench` 同样处理。

### 19.5 失败时的报错要能教人做事

`OpenMySQL` 按口令是否为空分成两条错误信息：

```
口令为空 → 连接 MySQL 127.0.0.1:3306 失败（用户 okx，口令为空）：…
           未配置 MySQL 口令。任选一种（改完重启 okxweb 生效）：
             ① 双击 scripts\set_db_pass.bat …
             ② 在 C:\…\finally\.mysql-pass 里写一行口令
             ③ 设环境变量 OKX_MYSQL_PASS
口令非空 → 连接 MySQL … 失败（用户 okx，口令来源：环境变量 OKX_MYSQL_PASS）：…
```

只说 `Access denied` 会让人以为「口令写错了」，而实际上根本没配。
另外**只报来源、不报口令** —— 日志经常被人截图贴出来。

### 19.6 轮换的设计：先验证再落盘，失败自动回退

`scripts\set_db_pass.bat` 的顺序（`--gen` 分支）：

```
① 用**旧**口令登录实测        ← 连不上就一行都不改
② mysql -e "SET PASSWORD = '<新>'"
③ 用**新**口令再实测          ← 不信 ① 的退出码，直接验
④ 成功 → 写 .mysql-pass + setx → 重启 OKXWeb
   失败 → 尝试用旧口令回连；旧口令还通 = 库没改成功
          → 把 .mysql-pass 恢复成旧口令，报告并退出
```

`SET PASSWORD` 是单条语句，要么生效要么没生效。与其猜退出码，不如改完直接验一次
—— 比「检查返回码然后相信它」可靠得多。**不需要 MySQL root**：
`okx` 账号可以改自己的口令（`SET PASSWORD`）。

### 19.7 实测证据（2026-10-01）

| 项 | 命令 | 结果 |
|---|---|---|
| 密钥文件来源 | `okxweb.exe -init-only` | `口令来源 : 密钥文件 C:\…\finally\.mysql-pass` → `MySQL 8.0.43 已连接` |
| 环境变量优先级 | `OKX_MYSQL_PASS=WRONG okxweb.exe -init-only` | **失败** —— 文件里口令是对的却照样失败，证明环境变量压过文件；错误里带 `口令来源：环境变量 OKX_MYSQL_PASS` |
| 环境变量正向 | `OKX_MYSQL_PASS=<正确> okxweb.exe -init-only` | 退出码 0，`已连接` |

`.mysql-pass`（`git check-ignore` 已确认被拦，不入库）。

### 19.8 三个批处理 / 脚本的坑（都能复现）

**(1) 无 BOM 的 `.ps1` 里的中文注释会吞掉代码行**

Windows PowerShell 5.1 读**没有 BOM** 的 `.ps1` 时按当前 ANSI 代码页解码
（中文 Windows 上是 GBK）。UTF-8 的中文注释被解成乱码，而乱码**可能把紧随其后的
代码行一起吞掉**。症状极具欺骗性：

```
ps1 exitcode=0
OK                       ← 脚本自己打印的成功信息
file size  = 0 bytes     ← 实际什么都没写
```

「退出码 0 + 打印成功 + 0 字节输出」。定位花了三轮实验（先怀疑 `for /f` 捕获、
再怀疑 `set /p`、最后才怀疑注释编码）。
**规则：`_newpass.ps1` 必须保持纯 ASCII**；中文说明写在调它的 `.bat` 里
（bat 是 GBK + CRLF，这台机器上验证过）。

**(2) 不要用 `for /f` 捕获 PowerShell 的 stdout**

启动失败（策略被拦、路径写错）时会往 stdout 打一屏横幅，`for /f` 会把这些横幅
逐行 `set` 进变量 —— 实测「随机口令」变成了一句更新提示。改成**写临时文件**后，
「没有文件」就是明确的失败信号。

**(3) `if ( ... )` 块里不要 `call` 之后立刻用 `%VAR%`**

块内所有 `%VAR%` 在「整块被读到」时就展开完了，而 `call` 是块执行时才跑的 ——
拿到的是调用前的空值。不报错，只是新口令永远为空。`set_db_pass.bat` 里为此
专门标注了「本段故意不用 if/else 块」。

> 顺带一条环境认知：`sc.exe` 在本沙箱里被程序黑名单拦截，会让 cmd **静默终止**。
> 所以 `start_all.bat` / `install_services.bat` 的改动要用「原文抽取 + 桩替换
> `sc`/`net`」的办法单独验证，不能直接整脚本跑。

## 二十、配置热插拔：改 JSON 即刻生效，绝不写死在 Go 里（2026-10-01）

### 20.1 口径：唯一真源是 `configs/okx_strategy.json`

`configs/` 目录下真正生效的配置**只有一个文件**：`configs/okx_strategy.json`
（`okx_strategy.example.json` 只是模板）。所有交易口径 —— 每笔保证金、杠杆、
准入上限 `max_order_margin_usdt`、成交额下限、排除规则、止盈、加仓、保留窗口 ——
**一律以这个 JSON 为准**。

Go 源码里出现的数字全部只是「**文件缺失 / 解析失败**时的兜底默认值」，
**不构成任何要求**。想让某个口径生效，改 JSON，不要改代码。

### 20.2 两条读取路径，曾经只有一条是热的

| 路径 | 谁在用 | 改动前 |
|---|---|---|
| `conf.LoadConfig()` | 自动交易引擎（下单/止盈/加仓）、归档/清理、日志 | ✅ **本来就热加载**：比对文件 mtime，改了自动重读 |
| `service.LoadStrategy()` | **合约准入过滤（symbolList）+ 网页展示** | ❌ **只在进程启动时读一次** |

后果很直接：改 `max_order_margin_usdt`（可买入金额）时，
**引擎那边的口径立刻变、symbolList 却纹丝不动**，必须重启 `OKXWeb` 服务才更新。
「明明改了配置怎么没生效」的困惑基本都出在这里。

### 20.3 补法：`service.StrategyStore`（`internal/service/strategy_store.go`）

```
Get()      先 os.Stat 挡一层（mtime/size 没变就直接返回缓存，不读文件）
           → 变了才读全文，算 sha256；与上次相同则视为「没变」
           → 真的不同才替换，并打一行差异日志
Watch()    每 2 秒轮询，只在「内容真的变了」时回调 → 立刻重算全市场准入
Force()    无条件重读；changed 告诉调用方要不要重跑下游
```

四个刻意的设计：

1. **用内容 sha256 判变化，不用 mtime**。编辑器「另存为」或 `copy` 会让 mtime 变
   而内容一模一样 —— 那种情况不该白跑一遍全市场过滤（一次要抓公告 + 全量算 480 个合约）。
2. **读失败沿用上一份，绝不打回默认值**。JSON 手滑写坏（少个逗号）时，
   如果拿 `LoadStrategy` 返回的默认值当真，整个策略会被**静默打回出厂设置**
   （准入放宽、止盈变 1%、dry_run 变 true……）。所以错误分支里只在
   「从来没有成功加载过」时才用默认值兜底。
3. **`Get()` 永不返回 nil**，调用方不用到处判空。
4. **顺手删掉了一条 Go 里的「要求」**。`strategyconf.go` 原来有一段：

   ```go
   if cfg.MaxOrderMarginUSDT < cfg.Entry.MarginUSDT {
       cfg.MaxOrderMarginUSDT = cfg.Entry.MarginUSDT   // ← 偷偷改掉你写的值
   }
   ```

   它本意是防呆，实际是错的：把准入上限**收紧**到比每笔保证金更低
   （每笔 1U，但只买最小一手 ≤0.5U 的合约）是完全合理的收紧，不该被改回去。
   现在只在「没填 / 写负数」时才回落兜底。

### 20.4 接线（三处）

```go
// cmd/okxweb/main.go
strategyStore := service.NewStrategyStore(cfgPath, cfgLog)

// ① 配置一变 → 立刻重算准入，symbolList 当场更新
go strategyStore.Watch(ctx, 2*time.Second, func(st *service.StrategyConfig) {
    fmt.Println("[CFG] 检测到策略配置变更 → 立刻重算合约准入（symbolList）")
    applyUniverseFilter(db, bf, strategyStore, *days)
})

// ② 准入过滤内部 st := store.Get() —— 热读，不是启动快照
func applyUniverseFilter(db, bf, store, days) { st := store.Get(); ... }

// ③ 接口层每次请求现取（internal/handler）
func (s *Server) cfg() *service.StrategyConfig { return s.strategy.Get() }
```

原来的 30 分钟兜底 tick **保留**：那是应对「外部世界变了」（新币老过 30 天、
成交额塌、新出下线公告），跟配置热插拔是两件事，不能互相替代。

|---|---|---|---|

### 20.6 ★ 一个必须记住的反直觉结论：放宽不等于变多

本轮把准入上限从 **1.0U 放宽到 1.5U**，但 symbolList **仍然是 176 个，一个没多**。
原因（用 `scope=all` 查全量分布查出来的）：

```
全量 480 个合约，最小一手保证金的分布：
  (0,   0.5] U : 452
  (0.5, 1.0] U :  23
  (1.0, 1.5] U :   4   ← 放宽本该新增的那 4 个
  (1.5, ∞  ) U :   0
```

那 4 个落在 1.0～1.5U 的合约（`MOONSHOT` / `AEHR` / `CSOPSAMSUNG2L` / `SPCH`）
**全是 `instCategory=3` 的美股/ETF**，被**规则 1 先行排除**了 —— 跟资金上限无关。
真正的加密合约里，当前最大的一手保证金只有 **0.73U**，所以 1.0U 和 1.5U 在
当下的市场上**完全等价**。

> 教训：**改完配置要看「为什么没变化」，别急着以为改动没生效。**
> 用 `scope=all` 把被排除的原因列出来（`excludeReason`），比盯着数字猜快得多。
> 这条口径本身是对的（以后有币落在 1.0～1.5U 会自动进来，而且热插拔即时生效），
> 只是当前行情用不上这 0.5U 的余量。

> **★ 三期后续（2026-10-02）：这个「以后」到了。★**
> 三期按用户口径关掉了规则 1（`exclude_stock_etf: false`），上面那 4 个被规则 1 挡住的
> **美股 / ETF 合约现在直接进来**，可交易数 **170 → 239**。
> 这正是 20.6 那条「放宽不等于变多」的反例 —— 当时的瓶颈**不是**资金上限，
> 而是另一条更前面的规则。**排查「放宽了没变多」时，必须按规则顺序看是谁先出局的。**

## 二十一、性能优化第一轮：pprof + 指标批量化 + 网络段并发 + 本地库优先（2026-10-01）

起因：用户问「项目所有文件能不能全部热插拔？全部用 C++ 编成 DLL 让 Go 调用会不会更快？」
结论是**不该换语言**（实测纯计算占实时扫描整轮墙钟 **0.06%**，按 `signal.recalc`
单次调用口径也只有 **0.21%**，详见 `docs/性能评估-Go与C++对比.md`），
转而把四个**真正的实现缺陷**修掉了。本章记录改了什么、为什么这么改、实测到什么。

### 21.1 先加 pprof（不改这个，后面全是猜）

**问题**：项目此前**没有** `net/http/pprof`。所有关于「瓶颈在哪」的判断都只能靠纸面推断 ——
而这一轮推断就错过一次（以为瓶颈在指标计算，实测 `signal.recalc` 单次调用里计算只占 0.21%）。

**做法**（`cmd/okxweb/main.go` 的 `startPprof`）：

* 新增 flag `-pprof-addr`，默认 `127.0.0.1:8091`，留空 = 关闭；
* **单开端口，绝不挂在 8090 上** —— 8090 被 Apache 反代到公网 80，
  挂上去等于把 goroutine 栈、命令行参数、堆快照送到全世界；
* **强制回环校验**（`pprofAddrIsLoopback`）：哪怕手滑传 `0.0.0.0:8091` 也直接拒绝启动。
  端口配错不该变成一次安全事件。只放行 `127.0.0.0/8` / `::1` / 字面量 `localhost`。

抓火焰图：

```bat
go tool pprof -http=:9999 "http://127.0.0.1:8091/debug/pprof/profile?seconds=30"
```

### 21.2 `ComputeSignal` 的 O(n²) 与 258KB/次 分配

**问题**（实测）：

* 老 `ComputeSignal(instID, bar, candles, idx)` 为了判**一根** K 线，
  把整段 1500 根的全部指标重算一遍 → 单次 335.9 µs / **258 KB / 23 次分配**；
* 逐根扫完整段就退化成 O(n²)：`bars1500` 逐根跑完 **440.6 ms / 361 MB / 35,838 次分配**；
* 后果：`numGC = 9,443`（**每秒 7.2 次 GC**），而 live heap 只有 3.5 MB —— 全是短命大对象。

**做法**（新增 `internal/service/indicator_series.go`）：

* `ComputeSeries(instID, bar, candles)` —— 指标**只算一遍**，之后 `At(idx)` 是 O(1)；
* `sync.Pool` 复用 `h/l/c/v` + 十几个指标数组（`indicatorScratch`），稳态下不再分配；
* `ComputeSignal` 保留为薄封装（池化取用 → 算 → 返回独立副本），**调用点一行不用改**；
* 原实现逐行保留为 `computeSignalReference`，**只作等价性测试的参照**。

**实测（2 核机器）**：

| 基准 | 改造前 | 改造后 | 改善 |
|---|---|---|---|
| `ComputeSignal` 判尾部一根 | 335.9 µs / 258,336 B / 23 allocs | **196.5 µs / 376 B / 2 allocs** | 耗时 −41%，**内存 −99.85%** |
| 逐根扫 1500 根（O(n²) 路径） | 440.6 ms / 361,697,328 B / 35,838 | **1.215 ms / 419,591 B / 6,188** | **耗时 363×，内存 861×** |

**★ 数值口径绝对不许变 ★**
公式、周期、NaN 填充范围、比较方向全部逐行照搬，只改「写到哪里」。
为什么必须比特一致：递归指标（ATR/RSI/EMA/TD9）的值**依赖窗口起始位置**，
差一个元素就会让买卖点漂移。等价性测试（`indicator_series_test.go`）覆盖：

1. 9 种长度 × 全部下标（含 −1 / n / n+1 等非法下标）逐字段比对；
2. 更真实的形态（上涨 → 急跌 → 横盘 → 再急跌 → 反弹，夹一根放量）；
3. **池化专用的「先长后短」污染测试** —— 长数组复用给短数组时，
   如果哪个指标函数没把全部位置写满就会读到旧值。这种 bug 只在
   「长 → 短」交替时出现，单次调用永远测不出来；
4. `Release()` 幂等、nil 接收者安全、空输入行为与改造前一致。

> 一个具体的复用陷阱：`tdSetup` 靠 `make` 把前 4 个元素默认成 0，
> 池化复用后它们会是上一轮留下的旧值 —— 必须显式清零。见 `tdSetupInto`。

### 21.3 `refreshLatestKlines`：串行网络循环 → 并发

**问题**（`internal/service/backfill.go`）：一个**串行 for 循环**遍历 479 个合约，
每个合约**一次 OKX HTTP 请求**：

```go
for k, maxTs := range known {
    ks, err := m.feed.FetchCandles(instID, bar, 3)   // ← 每次 ~130ms 网络等待
}
```

15m K 线收盘的**那一瞬间 479 个合约同时到期**，串行等价于「479 × 单次网络延迟」。
实测 `feed.refreshLatest` **平均 44.6 秒、最大 753.3 秒（12.5 分钟）**。

**做法**：拆成两段 ——

1. **筛到期任务**：纯内存判断（只读 `knownTs` 快照 + 比时间），串行，微秒级；
2. **抓最新一根**：worker pool 并发（`m.cfg.Workers`，默认 6），写法与 `scanner.go` 一致。

**⚠️ 收益天花板是限频闸门，不是并发数**：
`ratelimit.Candle()` = **20 次 / 2 秒**（扫描、回补、刷新共用同一把闸门，见 `internal/ratelimit`）。
479 条请求最少也要 **47.9 秒**，并发只能把「等网络」和「等闸门」重叠，**不可能突破这个地板**。
想再快只能减少请求数（例如只给可交易合约续 K 线）——那是产品口径变更，本轮不动。

### 21.4 实时扫描改读本地 MySQL（本地优先 + 落后回退）

**问题**：库里已经有 **1,364,329 行** K 线，而 `scanner.go` 每轮对每个候选合约
重新从 OKX 拉 400 根（`CandlesEnough` = 1 次 `/market/candles` + 1 次 `/market/history-candles`）。
单合约实测约 130 ms/次网络往返，而同样 400 根本地索引查询只要 1~5 ms。

**做法**：`loadCandles()` 优先读库，**任何一项对不上就回退网络**，判据是纯函数
`localCandlesFresh()`：

```
本地最新一根的 ts 必须 ≥ 当前「应该刚收盘」那根的开盘时间
   周期 dur、时刻 now → 正在走的这根开盘于 floor(now/dur)*dur
                    → 最后一根已收盘的 K 线开盘于 floor(now/dur)*dur − dur
```

判错方向只有一个后果：**拿着上一根 K 线算信号 → 漏单或重复下单**。
所以这段被抽成纯函数穷举单测（`scanner_local_test.go`）：

* 「刚好含最后一根已收盘」→ 可用；「还差一根」→ **必须回网络**；
* 根数 399 vs 400（差一根就不够暖机）→ 回网络；
* **停机两小时后重启**（库里数据落后 8 根）→ 必须回网络；
* `BarDurationMs` 解析不了的周期 → 回网络，不瞎猜。

另外两个容易被忽略的点：

1. **递归指标依赖窗口起始位置**，所以本地取的根数必须与网络路径**等长**，
   否则同一根 K 线会算出不同信号。网络路径是 `300 根 + 翻 1 页 100 根 = 400 根`
   （`minCandles` 一满足就停），所以本地也取 `minCandles` 根。
2. 库里的 `Confirm` 一律置 false，让 `IndexOfLastClosed` 走「按周期 + 时间推算」分支 ——
   库里可能存着**正在走的那根**（`refreshLatest` 会把它写进来），时间推算正好能排除它。
   测试里专门验证了「本地路径与网络路径必须选中同一个下标」。

**降级开关**：`Scan(cfg, cli, bar, kdb)` 的 `kdb` 传 `nil` 就完全退回改造前的纯网络行为；
`store.DB()` 拿不到句柄时 `trader.go` 也是传 nil。出问题的降级成本为零。

### 21.6 顺带纠正的一处归属错误

本轮开工时把 `signal.recalc`（平均 28.7 s）当成了实时扫描的埋点。
复核后发现它在 `sigbackfill.go:292`，是**历史信号回填**，不是实时扫描；
实时扫描的埋点是日志里的 `[15m] … 用时`。

两者成因不同，修法也不同：

* **回填**（`signal.recalc`）—— 逐根**滑动窗口**重算指标，计算密集。
  那时判断「窗口语义（`sigWindow=700`）不能用『全序列算一次』替代」，
  所以本轮只吃到池化带来的分配下降，算法没动。
  > ⚠️ **这条判断当天夜里就被推翻了**（见 §21.7）：窗口确实不能"想当然"替换，
  > 但**先取证再替换**是可行的 —— 实测 8400 个下标离散字段零差异，可以换。
* **实时扫描**（`Scan`）—— 每合约 2~3 次 OKX HTTP，网络密集。本轮已修（§21.4）。

> 教训：**打点名字不等于代码路径**。`signal.recalc` 听起来像实时扫描，
> 实际是回填。改之前必须回源码确认埋点位置，别照着名字推断。

### 21.7 第二轮：`live.exitPass` 的内部成本 与 `signal.recalc` 的逐根滑窗（2026-10-01 夜）

上一轮结束时（§21.5）留下了两个明确的未完成项：`live.exitPass`（28~56 秒）
和 `signal.recalc`（逐根滑动窗口重算）。这一轮把它们做完了。

#### 21.7.1 先拆打点，再改代码 —— 我的假设被自己的埋点证伪了

`live.exitPass` 的埋点原来包着**整段**逻辑，其中包括 `eng.mu.Lock()` 的排队等待。
读出来 13~65 秒，很自然会推断「是跟 `EngineRun` 抢锁抢的」。
**这个推断是错的。** 把它拆成两段后第一次读数就很干净：

```
live.exitPass = 20020 ms
live.exitWork = 20017 ms   ← 真正干活
live.exitWait =     3 ms   ← 等锁
runExits.boll = 17631 ms   ← 真凶，占了 exitWork 的 88%
```

> 教训：**「等锁」和「干活」必须分开打点。** 合在一起的计时器没法区分
> 「我的代码慢」和「我在排队」，而这两者的修法完全相反。

真凶是 `runExits.boll`：出场巡检对**每个持仓**都要判一次布林上轨，
每判一次走 `LatestSignal → CandlesEnough`，也就是**每个仓位 2 次 OKX HTTP**。
而 OKX 的 K 线接口挂着一把**全局共享**的限频闸门（20 次/2 秒），
回补、扫描、刷新、出场全都在抢同一把 —— 实测单次 `LatestSignal` 平均 **1.68 秒**，
其中绝大部分是**排队**，不是网络往返（单次 RTT 只有 116~201 ms）。

#### 21.7.2 修法：改数据来源，不改算法

数据本来就躺在本地库里：扫描器读 80 个合约的全部 K 线只要 **458 ms**（5.7 ms/合约）。
所以把出场、加仓两处的 K 线来源从「网络」换成「本地优先、落后回退网络」即可。

**但这里有一个必须踩对的坑，写错了不会报错、不会崩、日志也干净：**

| 转换函数 | `Confirm` 字段 | 谁在读它 |
|---|---|---|
| `klinesToCandles` | 恒 `false`（刻意） | `IndexOfLastClosed` 的「按周期+时间推算」分支 |
| `klinesToCandlesAt` | 按 `ts + 周期 <= now` 算出来 | `addon.go` 的 `closedWindow` —— **直接读字段** |

`closedWindow` 的实现里有 `if !c.Confirm { continue }`。如果图省事把
`klinesToCandles` 的输出喂给它，窗口会**恒为空** →
**加仓永远不触发**，而且一句错误日志都没有。

所以新增了 `loadCandlesLocal()`（本地优先、带 `Confirm`），
与 `loadCandles()`（本地优先、不带 `Confirm`）**并存而不是合并** ——
两个函数的差别只有 `Confirm` 一个字段，但用错的那个是静默故障。

`internal/service/klines_confirm_test.go` 就是守这个坑的：
`TestClosedWindowWorksWithLocalCandles` 断言 `klinesToCandlesAt` 的窗口 **≥ 2 根**、
`klinesToCandles` 的窗口 **恰好 0 根**；
`TestTwoConvertersAreDeliberatelyDifferent` 断言两者**只允许 `Confirm` 不同**，
OHLCV 必须逐位一致。

#### 21.7.3 `sigbackfill`：逐根滑窗 → 整段算一次

旧写法对第 i 根调一次 `ComputeSignal(win)`，而 `ComputeSignal` 每次都要把
**整个窗口**的指标重算一遍 → 整体 O(根数 × 700)。单合约 2900 根就要 255.5 ms，
175 个合约一轮 **46 秒**，而且纯串行吃满一个核也压不下去。

换成 `ComputeSeries`（整段算一遍，之后 `At(i)` 是 O(1)）：

| 基准（2900 根 / 合约） | ns/op | B/op | allocs/op |
|---|---|---|---|
| `BenchmarkSigBackfillWindowed`（旧） | 255,528,000 | 22,832,610 | 16,702 |
| `BenchmarkSigBackfillFullSeries`（新） | **1,819,600** | **942,944** | **11,432** |

**140×**，内存 −96%。175 个合约：44.7 s → **0.32 s**。

#### 21.7.4 口径取证：不能靠「我看着差不多」

滑窗法的第 i 根，递归指标（Wilder ATR / RSI / EMA）的**种子落在下标 i-699**；
整段法的种子落在下标 0。种子位置不同，值就会不同，所以**必须先把差量出来**。

理论量级：最慢的递归指标是 `period=96` 的 Wilder ATR，
残差 `(95/96)^700 ≈ 6.8e-04`。（我在动手前先按 EMA(26) 估成 `1e-23` —— **估错了**，
是 `Fri = atrp14/atrp96` 里的 `atrp96` 主导。）

实测（`internal/service/testdata/` 里 3 个主力合约 × 3000 根**真实** 15m K 线）：

| 合约 | 比对下标 | 浮点最大相对偏差 | 出现字段 | **mask / score / Td / Ready 不一致** |
|---|---|---|---|---|
| BTC-USDT-SWAP | 2800 | 6.593e-04 | `Fri`@2701 | **0** |
| ETH-USDT-SWAP | 2800 | 6.523e-04 | `Fri`@2665 | **0** |
| SOL-USDT-SWAP | 2800 | 4.604e-04 | `Fri`@1274 | **0** |

**8400 个下标，离散字段零差异。** 而且整段法的值**更准** ——
700 根窗口对 `period=96` 的 Wilder 平滑本来就是欠收敛的，整段法是单一种子。

回归门（两条都必须保持零差异，否则测试直接红）：

* `TestWindowedVsFullSeriesOnRealData` —— 真实 K 线
* `TestWindowedVsFullSeriesEquivalence` —— 合成 K 线

两条都调用**生产代码里的 `backfillSignalWindowed`**（旧的滑窗实现被刻意保留为
测试对照），不是测试里另抄一份 —— 这样生产实现一改，测试立刻红。

> 另一个必须知道的事实：`signals` 表是 `UNIQUE(inst_id,bar,ts)` + `INSERT IGNORE`，
> 所以**库里已经写好的历史行不会被这次改造改写**。重算只影响新写入的行。

#### 21.7.5 计算修完，瓶颈搬到 I/O —— 只读「真要算的那一段」

计算降到 0.32 s 之后，`signal.recalc` 一轮**仍是 40 秒**。原因很直接：
175 个合约每轮都 `QueryKlines` **整个合约的全部历史**（BTC 一年 35060 根），
一轮 **600 万行**的读库 + 解析，而真正要算的往往只有新到的那一两根。

改成按水位线分段读、最多读 `sigReadBars = 2000` 根：

* 取值依据：`N=2000 → 残差 9e-10`，比旧的 700 根窗口（`6.6e-04`）收敛**6 个数量级**；
  单合约读取量 35060 → 2000 根（**17.5×**）。
* 水位线左边可能有「新回补进来的老 K 线」，两块**在时间上不连续**，
  拼在一起会让指标跨断层计算。所以先用一次 `ToTs=<MinTs-1> LIMIT 1` 的探针
  确认左边没有缺口，才走快路；有缺口就退回全读。
* 探针走 `(inst_id,bar,ts)` 复合主键的反向索引，毫秒级。

线上取证（`tmp/mb51/cmd/sigverify`，直连线上 MySQL 只读）：


新增的 `TestProductionReadWindowMatchesFullHistory` 把这条固化进单元测试
（用 testdata 的 3000 根 vs 2000 根）。

#### 21.7.6 快路改造的副作用：原来的「秒退」失效了

这是个容易漏的地方。原来那句

```go
if sp.MaxTs > 0 && oldest >= sp.MinTs && newest <= sp.MaxTs { return 0, nil }
```

能触发，是因为旧代码每次都把**全部历史**读出来，`oldest/newest` 就是库里首尾。
改成只读一段之后，读回来的最早一根总是 `< sp.MinTs`，**那句秒退再也触发不了** ——
结果变成每轮给每个合约**白读 2000 根 + 白算一遍整段指标**。

用两次轻量探针把秒退找回来（`MAX(ts)` 看右边、`LIMIT 1` 看左边），
任一探针出错就**不返回**继续走慢路 —— 宁可多算一遍，不能因为一次查询失败漏掉新 K 线。

逐轮耗时（按 `/api/perf` 的 `avgMs × calls` 差分还原）：

| 版本 | 逐轮 `signal.recalc`（ms） | 中位 |
|---|---|---|
| 只加读取窗口（无早退） | 11860.8 / 3403 / 2565 / 2375 / 2462 / 2582 | 2573.6 |
| **加上无事早退** | 253 / 4148 / 185 / 337 / 200 / 177 / 198 | **200.5** |

稳态（没有新 K 线）**约 180~200 ms**，每 15 分钟才有一轮真的读+算是 2~4 秒。

#### 21.7.7 顺手修掉的诊断字段退化

`signal_scan_state.scanned` 被写成了 `len(asc)` —— 那只是**本次读回来的窗口长度**，
会把一年的 `35058` 写成 `2002`，看起来像「只扫了 2002 根」。
改成用已扫区间反推：`(MaxTs-MinTs)/dur + 1`。
加密货币永续 K 线连续（没有休市），所以这个值和 `COUNT(*)` 吻合 ——
实测 BTC 15m `(2025-10-01 13:15 ~ 2026-10-01 18:00) → 35060`，
库里 `COUNT(*)` 也是 **35060**；186 行全部自愈（`scanned=2002` 的行数归零）。

#### 21.7.9 还没做的

* **`eng.mu` 的锁拆分**：原计划把「整轮互斥」与「仓位变动互斥」拆成两把锁。
  但实测 `live.exitWait` 中位只有个位数毫秒 —— **性能上已经不值得做**。
  剩下的价值在交易安全性（避免用陈旧快照重复平仓/超额度开仓），属于另一个议题。
* **剩余大头已经是网络**：`exit.acct`（Balance + Positions，平均 285 ms / 最大 2488 ms）、
  `feed.syncTickers`（平均 1061 ms / 最大 4444 ms）。这些是 OKX 的 RTT 与限频，
  **换任何语言都不会变快** —— 这正是 §9.3「不要改 C++」结论的进一步证据。

> 一句话总结这一轮：**两个「看起来是计算问题」的瓶颈，一个是限频闸门排队，
> 一个是每轮把整个历史读出来。真正的修法是改数据来源和改读取范围，不是改算法、
> 更不是改语言。**

## 二十二、取消持仓 / 当日开仓上限，以及顺带挖出的「杠杆口径不一致」（2026-10-01 晚）

用户原话：

> 持仓和当日买入数量 不对 太少了 给我取消限制

### 22.1 先取证：到底是谁在拦

不看代码先看数据。`skip()` 的原因写在 `signals.reason` 里（不是日志），
所以直接按原因聚合当天（2026-10-01）的信号：

| 跳过原因 | 次数 | 性质 |
|---|---|---|
| 该合约已持仓 | 18 | **策略规则**（同合约不重复开），保留 |
| **当日开仓已达上限 30** | **5** | 计数上限，**要取消** |
| **持仓数已达上限 8** | **4** | 计数上限，**要取消** |
| （acted=0，无原因） | 12 | 历史回填写的信号，不参与决策 |

对照 `account.ordersToday = 33`、`posCount = 4~5`：
**当日笔数已经 33 > 30，早就满了**；持仓 4~5 个也贴着 8 在跑。
用户说「太少」是准确的。另外 `globalRiskBlock`（连亏 / 可用余额 / 总保证金占比）
当天一次都没触发 —— **不是风控在拦，就是这两条计数上限在拦**。

### 22.2 陷阱：光把 JSON 改成 0 是没用的

改之前 `internal/conf/config.go` 的 `fillDefaults` 里写的是：

```go
if e.MaxConcurrentPositions <= 0 { e.MaxConcurrentPositions = de.MaxConcurrentPositions } // → 8
if e.DailyMaxEntries <= 0        { e.DailyMaxEntries        = de.DailyMaxEntries }        // → 30
```

也就是说**配置文件里写 0 会被这几行反压回 8 / 30**，看起来改了、实际还在拦。
这类「兜底默认值压掉用户显式配置」的坑在本项目不是第一次出现
（见 §19 里 `applyMySQLFlags` 的 flag 默认值事件），所以这次专门盯住了它。

**三处必须一起改，缺一处都不生效：**

| 位置 | 改动 |
|---|---|
| `configs/okx_strategy.json` | `max_concurrent_positions: 8 → 0`、`daily_max_entries: 30 → 0` |
| `internal/conf/config.go` | 删掉这两条 `<= 0 → 默认值` 兜底；负数归一化成 0；**连默认值本身也改成 0** |
| `internal/service/trader.go` | 判定加 `> 0` 前置条件（否则 0 会变成「已达上限 0」，第一笔就被拦） |

### 22.3 语义：0 = 不限，而不是引入新哨兵值

同文件的其它字段本来就是这么设计的 ——
`risk.account_equity_stop = 0` = 不启用、`risk.max_total_margin_pct = 0` = 不启用、
`exit.max_hold_bars = 0` = 不启用、`exit.stop_loss_pct = 0` = 关闭。
所以这两个字段跟着用 **`<= 0` = 不限**，是同一个心智模型，不需要 `-1` 这种额外约定。

**默认值也一起改成 0** 是刻意的：万一 `entry` 块缺失、或键名拼错，
限制不会悄悄复活 —— 而「限制悄悄复活」正是这次用户反馈的现象。
真正的兜底交给账户可用余额与 `risk.*`。

`internal/service/strategyconf.go`（只给前端展示用）的兜底值同步改成 0，
避免两处口径不一致。前端 `web/assets/app.js` **完全没有引用这两个字段**，
只引用准入上限 `maxOrderMarginUsdt`，所以页面不用改。

### 22.4 上线即验证：同一根 K 线的 before / after

部署（19:17:43 重新加载配置）之后 17 秒，引擎就真的去下单了。
证据是 `signals` 表里**同一根 19:00 K 线**的两个不同结果：

| 时间 | 记录 |
|---|---|
| 部署前（18:30 / 18:45 / 19:00 三根） | `当日开仓已达上限 30` |
| **部署后 19:18:47** | `下单失败：OKX code=1 http=200 msg=All operations failed` |

**上限不再拦了，请求一路走到了 OKX 下单接口。** 日志同步佐证：

```
19:18:47 [ERROR] PROS-USDT-SWAP 下单失败：OKX code=1 http=200 msg=All operations failed
19:18:47 [INFO] [15m] … 信号 1 / 开仓 0 … 用时 3.52s
```

### 22.5 顺带挖出来的真问题：杠杆口径不一致

这一笔虽然不再被上限拦，但它**下单失败**了。失败链是：

```
[WARN] PROS-USDT-SWAP 设杠杆失败（继续下单）：OKX code=59102
       Leverage exceeds the maximum limit. Please lower the leverage.
[ERROR] PROS-USDT-SWAP 下单失败：OKX code=1 All operations failed
```

根因是**两条路用了不同的杠杆口径**：

* `internal/service/universe.go` 算「这笔买不买得起」时用的是
  `effLever(合约上限, 策略杠杆)` —— 已经是收敛过的；
* 而 `trader.go` 的 `calcSizeWith`（算张数）与 `SetLeverage`（真下单）
  用的是裸 `cfg.Entry.Leverage` = 20。

后果：OKX 有一批合约最高只给 10x，**准入按 10x 算「买得起」放行，
下单却按 20x 去 set-leverage 被拒，接着下单全失败**。

影响面是实测出来的（`inst.lever` 字段）：

| 口径 | 合约数 |
|---|---|
| 全市场 `state=live` 且加密类 | 174 |
| 最高杠杆 10x | 15 |
| 最高杠杆 20x | 95 |
| 最高杠杆 50x | 60 |
| **成交额前 80 名里最高只有 10x** | **4**（USELESS / CAP / ONE / PROS） |

也就是说**成交额前 80 的候选里有 4 个永远买不进来**，日志里只有一条 WARN
（后面那句「（继续下单）」还会让人以为没什么事）。

修法就是**复用现成的 `effLever`**（不新增函数、不新增 API 调用，
`Instrument.Lever` 本来就在手上）：

* `calcSizeWith`：`lev := float64(effLever(ins.Lever, cfg.Entry.Leverage))`
  —— 张数按真实杠杆算，单笔保证金仍是 1U 口径，只是名义价值随杠杆变小（**风险更小**）；
* `SetLeverage`：用同一个 `effLever`，并在真正发生收敛时打一条 INFO。

修完立刻生效（同一条 PROS 信号）：

```
19:21:43 [ERROR] PROS-USDT-SWAP 下单失败：OKX code=1 …      ← 修复前，连续 4 轮全失败
19:24:03 [INFO]  PROS-USDT-SWAP 合约最高 10x < 配置 20x，按 10x 下单
19:24:04 [SIGNAL] 开仓 PROS-USDT-SWAP 张数=14 开仓价=0.696500 共振 6/8
                  [摩擦,动能,RSI,布林,TD9,放量] 订单=3971215464397475840
```

`signals` 表里也出现了当天**第一条 `acted=1`（已下单）**。

### 22.6 没动的东西（以及为什么）

| 项 | 现状 | 说明 |
|---|---|---|
| `cooldown_bars = 6` | 保留 | 限制的是「**同一合约** 90 分钟内不重复开」，不是总持仓数 / 总笔数。用户没提，私改会影响策略节奏 |
| `该合约已持仓` | 保留 | 策略规则（同合约不重复开仓），当天拦了 18 次但没有它就会重复建仓 |
| `risk.*` | 全部保留 | `max_total_margin_pct=100` 是最实际的天花板 |
| `score_threshold` | **二期 6→8；三期 8→4；★ 五期 4→3** | 信号质量门槛。`score_threshold_map` 已清空（不再给 BTC/ETH 单独放宽）。★ 二期实测近 30 天 2329 条信号里 score 分布 6→2168、7→161、**8→0**，阈值 8 长期不出单；三期定为 4（= 当时口径 `score > 3`）并加「触发那根涨幅」附加条件，实测每周期能出 1~9 条；**五期按用户新口径定为 `3`（`Score >= 3`）且涨幅门槛降为 `0.5%`** —— 判定式本就非严格 `>=`，配置值与语义对齐 |
| `entry.min_bar_rise_pct` | **★ 六期 0.5（必须真涨）→ -0.7（必须真跌）** | 触发那根 K 线自己的涨跌幅门槛（**带符号**：> 0 = 必须真涨、< 0 = 必须真跌，比较都是严格的）。指针三态：不写=-0.7 / 写 0=关闭 / 写负数=「必须真跌」原样生效（**不许**归一化回默认）。买入、加仓、信号入库三处共用 `SignalQualified` |

**取消限制之后，真正的约束变成账户可用余额 + `risk.max_total_margin_pct`。**
这不是"没有刹车"，但刹车从「计数」换成了「资金」——
每笔 **0.1U** 保证金（三期口径；min_one 放大到最多 1U）、20x（部分合约 10x），持仓数上限由余额决定。
