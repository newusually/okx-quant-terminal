# 架构说明（三层 + 分层职责）

> 本项目已从「一个 mvc.go 装下所有东西」重构为 **接口层 / 业务层 / 数据层** 三层结构。
> 所有 Python 文件已全部移除，后端 100% 纯 Go，不需要装 Python、不需要 CGO。
>
> **2026-09-30 重大变更**：存储从 SQLite 换成 **MySQL 8.0**（400+ 合约并发写，SQLite 单写者模型扛不住），
> 对外入口从「Go 直接监听」换成 **Apache 80 反向代理 → 127.0.0.1:8090**。

## 一、运行拓扑

```
浏览器
  │  http://<本机IP>/            ← 只开 80
  ▼
Apache 2.4.68 (Windows 服务 OKXApache, 自动启动)
  │  mod_proxy_http + mod_deflate   80 → 127.0.0.1:8090
  ▼
okxweb.exe (Go, 只监听 127.0.0.1:8090)
  │  接口层 handler + 业务层 service + 数据层 repo
  ▼
MySQL 8.0.43 (Windows 服务 OKXMySQL, 自动启动, 127.0.0.1:3306)
```

三层全部安装在 `C:\Users\Administrator\Documents\finally` 下（`mysql/`、`apache/`、`bin/`），
不写注册表以外的任何系统目录，VC++ 运行库自包含在 `runtime/` 与 `apache/bin/`。

## 三、依赖方向（严格单向，不允许反向）

```
        cmd/*  (接口层入口)
          │
          ▼
      handler  ──────────┐
          │              │
          ▼              │
       service ──────────┤
       │     │           │
       │     ▼           │
       │    repo ────────┤
       │     │           │
       ▼     ▼           ▼
     model   conf      logx
```

* `model` 谁都不依赖，只放结构体。
* `service` 不依赖 `handler`，`repo` 不依赖 `service`。检验方式：改 `handler` 的代码永远不会
  导致 `service` 编译失败。
* 排除原因码统一定义在 `service/universe.go`（`ReasonStockETF` 等常量）与 `service.ExcludeLabel()`，
  `cmd/okxweb` 只写码、`handler` 只翻文案，两边永远不会漂移。

## 四、各层职责边界（改代码时的判断标准）

| 层 | 可以做 | 不可以做 |
|---|---|---|
| **handler** | 解析 HTTP 参数、拼 JSON、调 service/repo、写响应 | 写 SQL、算指标、决定要不要下单 |
| **service** | 业务规则、信号计算、风控闸门、准入过滤、编排多个 repo | 直接写 `http.ResponseWriter`、直接 `sql.Open` |
| **repo** | SQL、DDL、外部 API 调用、文件读写 | 判断「信号够不够强」「该不该平仓」 |
| **model** | 定义字段和 JSON 标签 | 任何 IO、任何业务逻辑 |
| **conf / logx** | 配置与日志自身 | 反向依赖 service / handler / repo |

## 五、合约准入（「哪些合约能买」）

唯一判定处：`service.FilterUniverse()`。规则按顺序执行，先命中先出局。

| # | 规则 | 实现 | 排除码 |
|---|---|---|---|
| 1 | 不买美股 / ETF / 商品 | `instCategory != "1"` | `stock_etf` / `commodity` / `category` |
| 2 | 不买刚上线的 | `listTime` 距今 < `exclude_new_listing_days`（默认 30 天） | `new_listing` |
| 3 | 不买要下线的 | OKX 公告中心 `announcements-delistings` 解析出的币种黑名单 | `delisting` |
| 4 | 24h 成交额下限 | `ticker.quote_vol24h < min_quote_volume_24h`（默认 100 万 U） | `low_volume` |
| 5 | 最小一手必须买得起 | `minSz × ctVal × ctMult × price ÷ lever ≤ max_order_margin_usdt`（默认 0.5U） | `notional` |

结论写回 `inst.tradeable` / `inst.exclude_reason`：

* **`tradeable` 只能由准入过滤写**。`UpsertInstruments` 的更新列里**故意不含**这两列——
  否则 10 分钟一轮的合约同步会把过滤结果冲回默认值 0（表现为「日志说 171 个可交易，
  网页列表一个都没有」）。
* 过滤每 30 分钟重跑一次（新币会老过 30 天、成交额会塌、公告会新出下线通知）。
* 公告黑名单自身有 **24h 缓存**（落在 `meta.delist_blacklist`），重跑不会打爆 OKX 接口。
* 公告标题里出现 `postpone / delay / resume / cancel` 视为「撤销下线」，
  会把更早的下线公告从名单里撤掉（例：`ONE` 先公告下线、次日公告推迟 → 保留）。

## 六、加仓（浮亏补仓 / 摊薄均价）

口径：**加仓额 = 原持仓保证金 × 1/3**；触发 = **15m 周期「先跌 0.5%」后「15m K 线转涨」**。

判定顺序（`service/decideAddon()`，纯计算、可单测）：

1. 加仓开关开着，且本仓加仓次数 `< max_times`（默认 3；只限制补仓，与出场无关）
2. 只取「开仓之后」的已收盘 15m K 线（开仓前的历史走势不算数）
3. 先跌：这批 K 线里出现过 `≤ 开仓价 × (1 - drop_pct%)` 的最低价
4. 低点必须落在最后一根之前（先跌 → 后涨，顺序不能反）
5. 后涨：最后一根已收盘 15m 是阳线（收 > 开）且收盘价高于前一根收盘价
6. 距上次加仓至少 `min_gap_bars` 根（同一根 K 线只加一次）

**加仓不新开持仓行**：`sz / entry_px(加权) / margin / addon_count / addon_margin / last_addon_ts`
就地合并进原行，所以止盈、布林上轨这些出场判定不用改也能按新均价算盈亏。

## 七、K 线分页（显示 1000 根 + 向左无限翻页）

前端一次加载 **1000 根**，鼠标向左滚到最前面时自动再取更早的 1000 根拼上去，可一直翻到库里最早一根。

### 接口

```
GET /api/mark?inst=ETH-USDT-SWAP&bar=15m&limit=1000            → 最新一页
GET /api/mark?inst=ETH-USDT-SWAP&bar=15m&limit=1000&before=TS  → TS 之前的 1000 根
```

响应里的 `page` 字段带翻页元信息：

| 字段 | 含义 |
|---|---|
| `firstTs` / `lastTs` | 本页最老 / 最新一根 |
| `hasMore` | 更早还有没有数据 |
| `earliestTs` | 库里该 (合约,周期) 的最老一根（翻到底了就停） |
| `totalBars` | 库里该 (合约,周期) 的总根数 |

### 关键实现：指标暖机

`MA99` 需要前 98 根、布林需要前 19 根。如果直接在「一页 1000 根」上算，
每页最前面 98 根就没有均线（表现为翻页后均线在缝上突然断掉）。

做法是 **多抓 99 根暖机段、在原始序列上算指标、再把暖机段连同指标一起裁掉**：

```go
const indicatorWarmup = 99
q := model.KlineQuery{InstID: inst, Bar: bar, Limit: limit + indicatorWarmup}
raw := db.QueryKlines(q)            // 1099 根
pg.Raw, pg.Trim = raw, len(raw)-limit
pg.Rows = raw[pg.Trim:]             // 输出 1000 根
// 指标在 pg.Raw 上算，再按 pg.Trim 对齐吐出 → 每页都是完整 1000 个均线点
```

同理，**同一个 bar 的均线值在哪一页里算都一样**（只要那一页带着它的前 98 根），
所以前端可以把每页的 `ma7/ma25/ma99/boll*` 直接按 `ts` 合并，不需要重算。

### 前端

* `state.klines` 保存已加载的全部 K 线（升序），`state.ind` 保存指标序列。
* `mergeByTs()` 按 `ts` 去重合并 —— 翻页时往前拼，定时刷新时覆盖尾部。
* 往前插数据后，`setVisibleLogicalRange({from: lr.from + shift, ...})` 保持画面不跳。
* `subscribeVisibleLogicalRangeChange` → 可视区落到第 `PAGE_TRIGGER` 根之前就预加载。
* `scrollGuardUntil` 压住 `fitContent` 触发的那次回调，避免一打开就把所有历史页拉下来。

## 八、K 线保留策略（「至少一个月」）

保留量按 **天** 而不是按 **根**（`keep_kline_days`，默认 30）：

```
15m 一天 96 根  ⟶  留 30 天 = 2880 根
```

> **2026-10-01：全库只保留 15m。**
> 1m/3m 先下线（占全表 69% 的行：1m 742 万 + 3m 674 万 / 全表 2009 万），
> 同日再把 5m/1H/4H 一起下架（用户口径：「只保留 15 分钟的信号和买卖点」）。
> 效果：kline 从 594 万行 → 137 万行，**okx 库 521MB → 132MB**。
> 权威名单在 `model.EnabledBars`，`/api/kline`、回补、信号回算三处共用。

余量从「×6/5 + 2 天（= 38 天）」收到「+1 天」：原来留 20%+2 天是为了
「每个周期至少覆盖一个月」，但口径已经明确成「只保留最近 30 天」，
38 天等于白存 27% 的行。回补侧同步加了 `backfill.trimToWindow(cfg.Days=30)`，
写入前就把超窗口的 K 线丢掉 —— 两边配合后「写进去又被删掉」的 churn 归零（详见 §十 之后）。

`CleanupKlines` 还会**顺手清掉不在白名单里的周期**（`SELECT DISTINCT bar` → 逐个整段删）：
旧版本回补进去的 5m 之类，按「保留 N 根」的逻辑是永远删不掉的，只会白占磁盘。

## 九、MySQL 高并发设计（400+ 合约）

| 手段 | 位置 | 作用 |
|---|---|---|
| 连接池 64 / 32 | `repo.MySQLConfig` | 6 个回补协程 + HTTP 线程共享，无排队 |
| 多行 `INSERT … ON DUPLICATE KEY UPDATE` | `repo.bulkUpsert` | 一轮一次网络往返，按 `batch_size=500` 分片 |
| `interpolateParams=true` | DSN | 免 prepare 往返 |
| `innodb_flush_log_at_trx_commit=2` | `conf/my.ini` | 日志不每事务 fsync，写入吞吐翻倍 |
| `innodb_autoinc_lock_mode=2` | `conf/my.ini` | 交错自增锁，批量插入不互相阻塞 |
| `skip_name_resolve=ON` | `conf/my.ini` | 跳过反解，每连接省一次 DNS |
| `performance_schema=OFF` | `conf/my.ini` | 2G 内存省下 ~200M |
| `innodb_buffer_pool_size=320M` | `conf/my.ini` | 按 2G 物理内存给的保守值 |

实测（`cmd/okxbench`，478 合约 × 6 周期 × 100 根 = **286,800 行/轮**）：
**11.4 ~ 12.7 秒/轮，吞吐 22.5k ~ 25.2k 行/秒，零失败**。

## 十一、这次重构顺手修掉的几个真实问题

1. **全部 `.py` 已删除**（22 个）。原来 `gorun.py / cash.py / sells.py / cashhistory.py /
   getuplRatio.py` 都 `from userinfo import User`，而仓库里根本没有 `userinfo.py`
   —— 也就是说那一整条链路从来跑不起来。
2. **`savecsv.py` 根本不存在**（`Savecsv` 一直在调一个不存在的脚本）。
3. **JSON 注释剥离的坑**：原来用正则 `//.*$` 去注释，会把 `"https://api.deepseek.com/v1"`
   里的 `//` 也当注释。现在统一走 `conf.StripJSONComments`。
4. **`SendDingMsg` 的 nil 解引用**：先 `defer resp.Body.Close()` 再判 err，请求失败会 panic。
5. **同一份数据两套结构**：`Instrument / Ticker / Kline …` 原本在 `runtime` 和 `web` 各定义一份。
   现在统一收敛到 `internal/model`。
6. **SQLite → MySQL**：`signal` 是 MySQL 保留字，表名改为 `signals`
   （`migrate()` 里带 `renameTableIfExists("signal","signals")` 自动迁移）。
7. **合约数只有 153 而不是 478**：`NewDataFeed` 误用了 `okx.FlagDemo`，
   OKX 收到 `x-simulated-trading:1` 头只返回模拟盘合约。改 `FlagLive` 后恢复 478。
8. **公告接口一直返回 401**：`GetAnnouncements` 走的是**带签名的私有请求**，
   而公告接口是**公开接口**。已给客户端加一条完全不带鉴权头的公共请求路径。
9. **`tradeable` 被同步冲掉**：`UpsertInstruments` 的更新列原本含 `tradeable`，
   10 分钟一轮的合约同步会把准入结果重置为 0。已把它排除出更新列。
10. **准入计数器复用**：`DroppedNotional` 曾同时被「成交额过滤」复用，
    导致 192 个「资金不够」实际是 61 个买不起 + 131 个成交额不足。已拆出 `DroppedVolume`。
11. **K 线滚动清理写死根数**：`CleanupKlines(30000)` 对 1m 只留 20.8 天、对 4H 留 13.7 年，
    都不满足「每个周期至少一个月」。改成按天（`keep_kline_days`）+ 按周期换算。
12. **分页指标断层**：暖机段在算指标之前就被裁掉了，导致每页最前面 98 根没有 MA99。
    改成在含暖机段的原始序列上算完指标、再同步裁掉暖机段。
13. **`conf.DefaultConfig` 未导出**：单测没法拿到「纯内置默认配置」，
    只能去读磁盘上的策略文件，测得不稳。已导出。

## 十四、OKX 历史仓位同步（2026-10-01 实测踩坑）

用户原话：「历史仓位根本不够看，这么多历史仓位只有 8 条记录」。
查下来**不是分页分少了，是分页参数用错了**。

### 14.1 `/account/positions-history` 的正确姿势

| 参数 | 实测结果 |
|---|---|
| `after=<posId>` | ❌ `{"code":"51000","msg":"Parameter after error"}` |
| `after=<毫秒时间戳>` | ✅ 返回**更早**的一批（语义 = 早于该毫秒） |
| `before=<posId>` / `before=<ms>` | ❌ `Parameter before error` |
| `begin` / `end` / `startTime` / `endTime` | ⚠️ **被静默忽略**：传 2026-04 的窗口，返回的还是最近那 100 条 |
| `limit=20` | ⚠️ 被忽略，**恒返回 100 条**（上限） |
| `type=1` | 返回 0 条 |
| `type=3` | ✅ 爆仓记录，覆盖 2024-12 起（和 type=2 是两个集合） |

网上大量示例写 `after=posId`，在这个接口上是**错的**。

### 14.2 `posId` 不是「一个仓位一个 ID」

OKX 按 **(合约, 方向, 保证金模式)** 分配 posId，平掉之后再开仓拿到的还是同一个。
实测 `ETH-USDT-SWAP` 一个 posId 底下挂了 **117 笔互不相干的交易**
（开仓价从 1718 到 2733 都有）。

所以幂等键必须是 **`posId` + 平仓时间(`uTime`)**（`repo.histKey`）。
只用 posId 当键 → 后一笔把前一笔覆盖，面板上永远只有 1 行 —— 这正是
「8 条记录」的另一半原因。

### 14.3 真实存量（2026-10-01 全量遍历）

| 口径 | 行数 | 唯一 posId | 跨度 |
|---|---|---|---|
| 不传 type | 6000+（60 页打满） | 560 | 2026-03-26 起 |
| type=3 爆仓 | 112 | 98 | 2024-12-09 起 |
| **最近 30 天** | **711** | **209** | — |

同步后本地 `trade` 表：**8 → 721 个已平仓仓位**（`[POSHIST]` 日志可自查）。
同步只往回取 35 天（`okxPositionsLookbackDays`），超过本地保留窗口的部分
由清理程序裁掉，没必要每次同步都拖 18 个月的数据。

> ⚠️ Windows 上从命令行拼 URL 时，命令替换出来的字符串尾部可能带 `\r`，
> 拼进去后 OKX 会**静默忽略非法参数并返回第一页** —— 表现是「翻页永远翻不动」。
> 所以所有出参统一走 `stringTrim()`。

## 十五、K 线「写进去又被删掉」的 churn（2026-10-01 修复）

### 症状
清理日志里 `kline` **每次稳定删 31,181 行、耗时 30~100 秒**，
而且删完几分钟又被写回来，无限循环。

### 根因（三段拼起来）
1. OKX `history-candles` 单次最多只给 **300 根**，而 300 根对不同周期是完全
   不同的跨度：5m = 1 天、15m = 3.1 天、1H = 12.5 天、**4H = 50 天**。
2. 回补把 300 根原样写库 → 4H 每个合约凭空多存 20 天数据（实测
   `max_cnt = 300`，正是那个 300）。
3. `CleanupKlines` 把 4H 裁到 `228 根 = 38 天` → 每次删 `(300-228)×479 ≈ 31,181` 行。

### 修法
* `backfill.trimToWindow()`：**写入前**丢掉 `ts < now - cfg.Days` 的 K 线。
* `CleanupKlines` 从 `trader` 的「每 20 轮」路径上摘掉 —— 它要 30~100 秒，
  挂在 20 分钟一次的路径上等于每 20 分钟把数据库按住两分钟
  （表现就是 K 线迟迟不更新、`live.exitPass` 从 3 秒涨到 26 秒）。
* 清理收敛成**一个入口**：`service.StartRetentionCleaner`，**一周一次**。

### 验收
| 指标 | 修复前 | 修复后 |
|---|---|---|
| 4H 行数 | 6 分钟内 104,797 → 135,978（反复） | 150 秒采样**恒为 104,797** |
| 清理删 K 线 | 每轮 31,181 行 | **0 行** |
| K 线裁剪触发点 | 3 处（trader 20 分钟 / backfill 6h / cleaner 6h） | 1 处（cleaner 每周） |

> 剩下的 72 秒耗时全部来自 1916 次「定位第 N 根」的 `ORDER BY ts DESC LIMIT 1 OFFSET ?`
> ——分区表没法用全局索引，每次要在 20 个分区上归并。
> 一周一次 → 占空比 0.012%，可以忽略。

## 十六、MySQL data 目录为什么“虚胖”（2026-10-01 排查）

用户问：「为什么 MySQL 的 data 目录那么大，是不是没删除干净？」

结论：**表数据删干净了，胖的是 binlog —— 而且是一行配置写错造成的。**

### 16.1 现场

| 目录 / 文件 | 占用 | 说明 |
|---|---|---|
| `OFF.000001` ~ `OFF.000023` + `OFF.index` | **3.27 GB** | 二进制日志（binlog） |
| `#innodb_redo/` | 193 MB | InnoDB redo |
| `undo_001` + `undo_002` | 302 MB | undo 表空间 |
| `okx/`（真正的表数据） | **200 MB** | 库内数据 131.6MB + 索引 |
| **合计** | **4.1 GB** | |

### 16.2 根因：`log_bin = OFF` 不是“关闭”

```ini
# conf/my.ini（错误写法）
log_bin = OFF
```

`log_bin` 是**接受文件名的选项**，MySQL 把 `OFF` 当成日志文件名 → 实际效果是：

```
log_bin          = ON
log_bin_basename = C:/.../data/OFF      ← 日志文件就叫 OFF
```

然后在 data 目录里默默攒 `OFF.000001 … OFF.000023`。
`binlog_expire_logs_seconds` 默认 30 天，所以几天的密集写入就堆到 3.6GB 也不会自己清。

这台机是**单实例、无主从复制、也不需要按时间点恢复**（K 线的源头是 OKX），
所以正确做法是彻底关掉：

```ini
# conf/my.ini（正确写法）
skip-log-bin          # 不是 log_bin = OFF
```

> 对比：`general_log = OFF` 是对的 —— `general_log` 是布尔变量，OFF 就是关。
> 踩坑的是 `log_bin` 这种「选项值为文件名」的变量。

### 16.3 一并收拾的另外两个

```ini
# 8.0.30+ 已废弃 innodb_log_file_size / innodb_log_files_in_group（只能用它们反推容量）
innodb_redo_log_capacity = 64M     # 原来按废弃参数算出 192M，2G 内存机器太奢侈
innodb_max_undo_log_size = 64M     # 配合 innodb_undo_log_truncate=ON 自动回收
```

### 16.4 处理与验收

1. 停 OKXWeb → 停 OKXMySQL
2. 改 `conf/my.ini`（`skip-log-bin` + redo/undo 两个上限）
3. 删掉 `mysql/data/OFF.*`（23 个 binlog + `OFF.index`）
4. 启 OKXMySQL → 启 OKXWeb

| 指标 | 处理前 | 处理后 |
|---|---|---|
| `mysql/data` | 4.1 GB | **676 MB** |
| `log_bin` / `log_bin_basename` | `ON` / `...\data\OFF` | **`OFF` / 空** |
| `#innodb_redo` | 193 MB | **65 MB** |

> ⚠️ 以后**不要**再把 `log-bin` 交给某个脚本去 append；
> 这个坑的隐蔽之处在于「配置看起来是对的、MySQL 也不报错、日志文件还正常在涨」。

## 十七、全库瘦身到「只留 15m · 只留 30 天」（2026-10-01）

### 17.1 用户口径

> 「清除多余数据 只保留 30 天的数据，把 4H 1H 5m 全部删除，只保留 15 分钟的信号和买卖点；
>   选项卡删除其他分钟数；检查数据库是否还有其它数据，只保留应该保留的信号、买卖点、持仓、交易等信息。
>   每周清理一次不变。」

拆成四条：**① 数据只留 30 天 ② K 线/信号只留 15m ③ 前端只剩 15m 选项卡 ④ 清理周期 = 每周一次**。

### 17.2 为什么 `kline` 只能「重建表」而不能 `DELETE`

```sql
-- kline 是分区表：PARTITION BY RANGE COLUMNS(ts)
-- bar 不是分区键 → 下面这条要扫遍所有分区，无法分区裁剪
DELETE FROM kline WHERE bar <> '15m';   -- ❌ 全分区扫（1.9 亿行时代要跑十几分钟）
```

`bar` 虽然排在主键 `(inst_id, bar, ts)` 的第二位，但它**不是最左前缀**，
优化器用不上索引定位。所以整表瘦身走「建新表 + `INSERT SELECT` + `RENAME` + `DROP`」，
见 `scripts/sql/slim_to_15m.sql`。

> 反过来，**行数不多时**分批 `DELETE ... LIMIT 20000` 就够了 ——
> 本轮删旧 exe 遗留的 14.4 万行 5m（占全表 9.5%），7 批 + 1 尾批，秒级完成。

### 17.3 两处「写进去又被删掉」的新 churn

#### ① POSHIST 的 lookback 比清理红线多 5 天

```go
const okxPositionsLookbackDays = 35   // ❌ 清理红线是 30 天
```

后果是一个**永久拉锯**：30~35 天那一档的仓位，

```
每 10 分钟  POSHIST 同步写入  →  每周  PurgeExpired 删掉  →  再写入  →  再删 …
```

日志表现就是 `[CLEAN] trade 删了 88 行` 反复出现，看着像一直没清干净。

```go
// ✅ 下界直接对齐保留窗口：多翻无收益，只会制造 churn
func okxPositionsLookbackDays() int { return repo.RetainDays() }
```

**实测证据**（同一进程，只换了这行）：

| 同步时刻 | 覆盖范围起点 | 对应窗口 |
|---|---|---|
| 11:40:53 | `2026-08-27 14:07` | 35 天 ❌ |
| 11:44:00 | `2026-08-27 14:07` | 35 天 ❌ |
| **11:45:45** | **`2026-09-08 20:17`** | **30 天 ✅** |

#### ② OKX 翻页天然会多带一页

`after=<毫秒>` 的语义是「平仓时间**早于**该毫秒的下一批」，
所以「翻过下界就 `break`」这个判断**必然发生在 `append` 之后** ——
每轮同步都会多带回一整页（最多 100 行，可横跨十几天）。

```go
t := atoi64(ut)
if t > 0 && (oldest == 0 || t < oldest) { oldest = t }  // 游标先算
if sinceMs > 0 && t > 0 && t < sinceMs { continue }     // ★ 窗口外直接丢，不 append
```

### 17.4 前端选项卡是「数据驱动」的，不用改 HTML

周期按钮由 `state.bars` 渲染：

```js
// web/assets/app.js
function renderTimeframes() {
  state.bars.forEach((b) => { /* 生成 .tf 按钮 */ });
}
```

`state.bars` 来自后端 `/api/state` 的 `bars` 字段 →
**只要后端只报 `["15m"]`，前端就自动只剩一个选项卡**，
`web/assets/index.html` 里根本没有硬编码的周期按钮（只有 `#tfGroup` 占位容器）。
所以「删除其它分钟数选项卡」＝ 改后端白名单 + 重新编译，不动 HTML。

### 18.1 用户口径

第十七节的「只留 15m · 只留 30 天」是本轮的**起点**，用户在当天进一步改了口径：

> 「还是修改一下 15 分钟 一年数据保留，其余的分文件上传到 github 中，

> 一年才运行一次清除任务就行。如果每个月月底 C 盘剩余总量小于 10G 余额，
> 就删除掉多余的之前几个月的数据、只保留当月数据就行。另外每个月要清除所有超过
> 一个月的日志记录，包括数据库、客户端、网页等日志，自动运行，并且清理回收站的
> 垃圾文件，最后上传最终版到 github 同步。」

拆成 **8 条硬需求**：

| # | 需求 | 落点 |
|---|---|---|
| 1 | 15m K 线保留期 30 天 → **1 年** | `store.kline_retain_days = 365` |
| 2 | 每月月底按月份分片导出并**自动**上传 GitHub | `archive.go` + 月度任务第 ①② 步 |
| 3 | **每年**清一次超过 1 年的数据（一年只跑一次） | `RunYearlyMaintenance` |
| 4 | 月底 C 盘可用 < 10G → 删旧月、**只留当月** | 月度任务第 ⑤ 步「磁盘守卫」 |
| 5 | 每月清所有**超过 1 个月**的日志（DB / 客户端 / 网页） | 月度任务第 ④ 步 |
| 6 | 全自动，不人工干预 | 服务内 30 分钟 tick + meta 表 |
| 7 | 清**回收站**垃圾 | `recycle_windows.go` |
| 8 | 最后把最终版推 GitHub 同步 | `scripts\push_github.bat` |

### 18.2 为什么是「三条独立红线」而不是一条

关键认识：**不同类型的行，增长速率差 3 个数量级**，塞进同一个窗口一定出事。

| 类别 | 代表表 / 对象 | 增速 | 保留窗口 | 由谁清 | 频率 |
|---|---|---|---|---|---|
| **记录表** | `trade` `trade_event` `signals` `equity` `runlog` `ai_call` `pnl_point` | `equity` **每 3 秒 1 条** → 留一年 = **1000 万行** | `store.retain_days = 30` | `RunRetentionCleanup` | **月度** |
| **K 线** | `kline`（只有 15m） | 479 合约 × 96 根/天 ≈ **4.6 万行/天** → 一年 ≈ **1700 万行** | `store.kline_retain_days = 365` | `RunYearlyMaintenance` | **年度** |
| **日志文件** | `logs\*.log`、`logs\archive\**`、`logs\shots\**`、`apache\logs\*` | 几十 MB/天 | `store.log_retain_days = 30` | `purgeAllLogs` | **月度** |

一句话：**权益曲线留一年没意义（谁会看三个月前某 3 秒的浮盈），但 K 线必须留一年，因为要拿来做回测。**
所以窗口必须拆开，不能共用一个 `retain_days`。

> 顺带修掉一个隐藏的语义混用：`backfill` 的 `cfg.Days` 和存储层的保留窗口是**两件事**。
> - `cfg.Days`（`-days 365`）= 回补时“往回想拉多远”
> - `repo.KlineRetainDays()`（`kline_retain_days = 365`）= “库里留多久”
>
> 第十七节的 `trimToWindow` 用的是 `cfg.Days`。如果保留窗口设 365、回补窗口还是 30，
> 那么刚拉回来的 300 天历史会被当成“超期数据”当场删掉 —— 白拉。
> 现已统一改为读 `repo.KlineRetainDays()`。

### 18.3 `kline` 是 RANGE COLUMNS 分区表 → 删数据应该 `DROP PARTITION`

第十七节§17.2 记过一个结论：`DELETE FROM kline WHERE ts < ?` 扫千万行是灾难。现在有了年份级红线，
这个问题必须正面解决 —— 而 `kline` 本来就是分区表：

| 分区名 | 含义 | 粒度 |
|---|---|---|
| `p_old` | 兜底垃圾桶（所有 `< 2026-09` 的历史） | 无 |
| `p202609` … | 冷区，落在一年以前的老月份 | **月** |
| `pw20260901` … | 热区，最近 8 周 | **周** |
| `pmax` | 兜底（未来时间戳） | 无 |

`ALTER TABLE kline DROP PARTITION pw20260801, ...` 是 **毫秒级**的：直接删数据文件，
**不产生 undo / redo / binlog**，也就不会像 `DELETE` 那样把 60GB 磁盘写爆。
一年级的清理用 `DELETE` 是**不可接受**的 —— 这就是要做分区删除的全部理由。

#### 选区规则（必须保守）

```go
// internal/repo/kline_repo.go
for _, r := range parts {
    if r.IsMax || r.Name == partitionOldName {   // pmax / p_old 永不删
        continue
    }
    if r.LessThan <= cutMs {                     // 上界 100% 落在 cutoff 之前
        hit = append(hit, r)
    }
}
```

「只有分区**上界 ≤ cutoff** 才整段 DROP」。直觉上看着保守，但它是**唯一正确**的判据：
上界 ≤ cutoff 才代表这个分区里**每一行**都过期；只要有一行没过期，整个分区就不能动。

只读验证（`cutoff = 2026-10-01`）：

```
命中：pw20260801 pw20260808 pw20260815 pw20260822 pw20260829
      pw20260905 pw20260912 pw20260919      ← 8 个，全部上界 ≤ 10-01
未命中：pw20260926（覆盖到 2026-10-03）       ← 正确放过
cutoff = 2025-10-01 → 0 个
```

`p_old` / `pmax` 无论 cutoff 多大多**永不 DROP** —— 它们是兜底桶，删掉等于把不属于任何
时间段的孤儿行连桶一起扔了。兜底交给 `PurgeKlineBefore(cutMs)`：

```sql
DELETE FROM kline WHERE ts < ? LIMIT 5000     -- 批间 time.Sleep(20ms)，上限 4000 轮
```

`dropKlineBefore(cutMs)` = 先 `DropKlinePartitionsBefore` 再 `PurgeKlineBefore`，两者都必须跑。

### 18.4 调度：用 meta 表记「上次跑的月份」而不是定时器

**不能用 Windows 计划任务** —— 这台机器上 `schtasks.exe` 被安全策略拦掉（实测）。
也不能用 Go 的 `time.Ticker` 直接算「月底」：机器会重启、服务会被拉停，
「月底那一刻进程恰好活着」是不保证的。

所以做成 **幂等 + 月/年粒度**：

```go
const (
    maintTickInterval = 30 * time.Minute   // 30 分钟比对一次
    maintFirstDelay   = 90 * time.Second   // 启动 90 秒后才开始，别抢启动资源
    metaLastMonthly   = "maint_last_monthly"
    metaLastYearly    = "maint_last_yearly"
)
```

`RunDueMaintenance()` 每次 tick 读 meta 里的 `maint_last_monthly`，
和 `now.Format("2006-01")` 比对，**不同才跑**，跑完写回当前月份。

好处：**停机三天、重启二十次，这个月的任务也只跑一次 —— 不重不漏。**
首次部署时把 `maint_last_monthly` 种子化为当月（`2026-10`），
所以**部署瞬间不会触发真实的回收站清理**，第一次真实月度任务落在 11-01。

```go
// 本质就这几行
if meta[metaLastMonthly] == now.Format("2006-01") {
    return  // 本月已跑过
}
runMonthly()
meta[metaLastMonthly] = now.Format("2006-01")
```

### 18.5 月度任务的 6 步顺序 —— **推送必须在磁盘守卫之前**

```
① 归档上月 K 线 → archive/kline-15m-YYYY-MM.partNN.csv.gz + manifest-YYYY-MM.json
② 推送 GitHub（数据仓）        ← ★ 必须在 ③/⑤ 之前 ★
③ 记录表清理（30 天）
④ 日志清理（30 天，DB + apache + 客户端）
⑤ 磁盘守卫（C 盘 < 10 GB → 删旧月、只留当月）
⑥ 清回收站
```

第 ② 步必须在 ⑤ 之前，理由是**顺序决定生死**：
如果先跑磁盘守卫把旧月份归档删了，再推 GitHub —— 一旦推送失败（断网、token 过期），
**归档本地没了、远端也没有，数据永久丢失**。先推后删，最坏情况只是「磁盘紧张一会儿」。

同理 ① 之前不会去删任何东西，② 若失败会记 `rep.ArchiveErr` / `rep.PushErr`
并**跳过 ③④⑤⑥ 里所有破坏性动作**（宁可这个月不清理，也不能把没备份的数据删掉）。

### 18.6 归档格式：为什么按「压缩后字节」滚动分片

**GitHub 单文件硬上限 100 MB**。经验值是「每片 20 万行」，但这是**魔数**：
不同月份的行数、币价精度不同，压缩比能差 3 倍（1.33M 行 → 17.4 MB，也可能同样是
1.33M 行 → 90 MB）。**押行数就是在赌**。

所以按 **压缩后字节数** 滚动，`archiveChunkBytes = 40 << 20`（40 MB）留足余量：

```go
if cw.n >= archiveChunkBytes {   // countingWriter 统计的是 gzip 之后、落盘的真实字节
    sealPart(); openPart(next)
}
```

`countingWriter` 包在 `gzip.Writer` **下面**（即最靠近文件的那一层），
所以它数出来的就是文件真实大小，不是 CSV 行宽估算。

#### ★ 收尾顺序绝对不能反 ★

```go
// sealPart 闭包：先 flush + close，再统计行数/字节/哈希
sealPart := func() error {
    csvw.Flush()                    // ① 吐出 CSV 缓冲里最后不到 2 万行
    if err := csvw.Error(); err != nil { ... }
    gz.Close()                      // ② 补写 gzip 尾部 8 字节（CRC32 + 原始长度）
    file.Close()                    // ③ 真正落盘
    part.Rows   = partRows          // ④ 这时候统计才是对的
    part.Bytes  = cw.n
    part.Sha256 = hex.EncodeToString(hash.Sum(nil))
    ...
}
```

踩过的坑：最初在 `gz.Close()` **之前**统计 → 清单里少算了 **22,649 字节**，
`sha256` 和实际文件对不上 → 校验必然失败。这两步（CSV 缓冲残留、gzip 尾部）
只在 close 之后才存在于文件里。

#### 清单（manifest）与校验

`manifest-YYYY-MM.json` 记录 `month / bar / source / from / to / insts / totalRows /
totalBytes / columns / tsUnit / parts[]`，每个 part 带自己的 `name / rows / bytes / sha256`。

实测（2026-09）：

```
kline-15m-2026-09.part01.csv.gz   18,293,379 字节
rows  1,336,768      合约 479      耗时 27 秒      分片 1 个
sha256 e9952ff5e7a583ce…   ← 重新计算后与清单完全一致
gzip -t 通过 / CSV 表头正确
```

注意 `tsUnit` 字段：`ts` 存的是**毫秒**。而 CSV 里用 `f2s`
（`strconv.FormatFloat(v,'f',-1,64)`）而不是 `%.2f` —— 否则小币价会全部写成 `0.00`，
回滚数据直接报废。

### 18.8 回收站：为什么不能用 `SHEmptyRecycleBin`

直觉做法是 Windows Shell API `SHEmptyRecycleBin(NULL, NULL, SHERB_NOCONFIRMATION)`。
**在这台机器上它是坏的**，原因有两层：

1. **Session 0 / LocalSystem**：`okxweb` 是 Windows 服务，跑在 `Session 0`，
   身份是 `LocalSystem`。`SHEmptyRecycleBin` 清的是**调用者自己那份**回收站 ——
   也就是 SYSTEM 的空回收站，清完什么都没发生。
2. **回收站是按用户隔离的**：文件实体在 `C:\$Recycle.Bin\<SID>\` 下，
   每个用户一个 SID 目录。你真要清的是 `Administrator` 那份，SYSTEM 看不到。

所以直接走文件系统：遍历 `C:\$Recycle.Bin` 下**形如 SID 的目录**
（`isSIDDir`：`S-1-` 前缀 + 只含数字和 `-`），逐个 `WalkDir` 删文件，
再**第二遍自下而上删空目录**（顺序反了删不掉）。

```go
RecycleBinRoot = `C:\$Recycle.Bin`   // recycle_windows.go
// 结果结构
type RecycleResult struct { Roots, Items, Bytes, Dirs, Skipped int; DryRun bool; Err string }
```

权限不足时 `res.Skipped++` 并**继续**，不中断整轮清理 —— 别的用户目录删不掉不该拖垮全流程。

> 这个操作**不可逆**，所以配了反向开关 `store.disable_recycle_clean`（默认 `false` = 清）。
> 想保留就直接改成 `true`。
>
> 预演实测：**5,686 个文件 / 287.1 MB / 0 个目录 / 跳过 0 项**，耗时 331 ms。

### 18.11 GitHub 推送脚本

`scripts\push_github.bat`，用法 `push_github.bat [code|data|check]`：

| 模式 | 动作 |
|---|---|
| `check` | 只打印远端连通性与待推送提交数，不推 |
| `code` | 推代码仓 `github.com/newusually/okx-quant-terminal.git` |
| `data` | 推数据仓 `github.com/newusually/okx-quant-terminal-data.git`（`archive/` 是独立 git 仓库） |

凭据优先级：`%ROOT%\.git-token`（一行 PAT）→ `%GITHUB_TOKEN%` 环境变量。
**都没有则 `exit /b 2` 干净退出，绝不卡在交互式用户名提示上** —— 服务里跑的命令，
一旦卡在提示符上就是永久挂起，所以 `cmd.Env` 里强制注入：

```
GIT_TERMINAL_PROMPT=0
GCM_INTERACTIVE=never
```

推送用**带 token 的临时 URL**，不写进 `.git/config`：

```
git push "https://x-access-token:%TOKEN%@%REPO%" HEAD:%BRANCH%
```

这样 `.git/config` 里不会留下凭据明文，`.git-token` 也已在 `.gitignore` 里。

调用侧（`cleanup.go`）：

```go
exec.CommandContext(ctx, "cmd", "/c", bat, what)   // 15 分钟超时
```
